# Mint 项目面试问答：口述分层版

整理日期：2026-09-30

> 使用说明：每题先用“20 秒直接回答”回应问题；面试官继续追问时，再展开“60 秒 STAR/取舍版本”；最后的“深挖追问与证据”用于准备追问，不建议一次性全部说出。
>
> 范围说明：本文基于 `docs/mint-project-interview-qa.md` 重组，不替代原始完整稿。项目当前存在并行重构，凡涉及记忆门控、Jev、服务目录或运行时链路的代码位置与现状，正式面试前应基于目标分支再次核对。

## 一、产品动机与架构

### 1. 市面上已有 ima、Obsidian 等产品，为什么还要做 Mint？

#### 20 秒直接回答

Mint 不是为了替代 ima 或 Obsidian，而是解决我自己的一个具体问题：资料存下来以后，仍然很难持续检索、核验和修正。我的目标是把资料摄入、Wiki 整理、混合检索、带来源回答和运行观察连成一条本地工作流，验证个人知识库能否做到可积累、可检索、可溯源。

#### 60 秒 STAR/取舍版本

- **S（背景）**：资料不断增加，但收藏和存储不等于未来能够准确使用；普通问答也很难说明答案依据了什么。
- **T（目标）**：做一个面向个人、本地资料的知识工作流，让用户既能得到答案，也能回到来源检查和修订。
- **A（行动）**：我把原始资料、Wiki 页面、FTS/向量检索、引用回答和运行观察串在一起，并保留原始来源作为核验入口。
- **R（结果与取舍）**：Mint 验证了这条链路在本地场景中的可行性。它的差异点是完整工作流和证据边界，而不是宣称竞品做不到；代价是摄入、索引和知识状态的一致性更复杂。

#### 深挖追问与证据

- 追问：核心用户是谁？目前主要是个人、本地、持续积累资料的用户，而不是多人企业知识库。
- 追问：差异是否只是功能拼装？回答重点应落在“来源可检查、索引可重建、失败可观察”的系统边界。
- 证据：原始资料、Wiki 页面、检索结果和引用链路可以分别检查；不要声称已经证明产品市场匹配。

### 2. 为什么选择 Karpathy 的 LLM Wiki 方案？

#### 20 秒直接回答

我看中的是它把原始资料和整理后的 Wiki 页面分开：原文保留，模型把内容编译成可查看、可修改的结构化页面。这样知识可以持续沉淀，而不是每次回答都临时拼接原始文件；但模型整理不等于事实正确，所以仍要保留来源追溯和人工修订。

#### 60 秒 STAR/取舍版本

- **S**：直接对原始文件做临时 RAG，知识结构难以复用，也不利于用户检查和修订。
- **T**：建立一个既保留原文、又能逐步形成可维护知识页面的中间层。
- **A**：采用“原始资料 → Wiki 编译 → 页面检索 → 引用回答”的链路，让页面成为可见、可编辑的知识资产。
- **R**：它降低了重复整理成本，并使知识结构可持续演进；代价是编译内容可能失真，因此不能把 Wiki 页面当成自动正确的事实源。

#### 深挖追问与证据

- 追问：为什么不直接检索原文？Wiki 页面提供更稳定的结构和可维护入口，但原文仍应保留用于核验。
- 追问：如何处理编译错误？通过来源链接、证据片段、lint 和人工修订发现问题，而不是假设模型输出正确。
- 证据：回答时区分“来源可追溯”和“来源真实”。

### 3. 这个项目是独立做的还是团队协作？你负责什么？

#### 20 秒直接回答

Mint 是我主导的个人项目。我负责产品方向、架构、全栈实现、Electron 集成、SDD、Harness 和 RAG Eval。SQLite、Embedding 服务和 Jev 是外部能力，我负责的是选型、集成、业务边界和验证，不会把底层模型或数据库能力说成从零开发。

#### 60 秒 STAR/取舍版本

- **S**：项目需要同时验证桌面端、本地知识库、Agent Runtime 和评测闭环。
- **T**：在个人项目资源有限的情况下，完成端到端可运行系统，并为关键能力建立验证方法。
- **A**：我负责需求拆解、架构设计、前后端和 Electron 实现，同时建立 SDD 文档、Harness 验收和 RAG Eval；外部组件通过明确接口接入。
- **R**：形成了从资料摄入到 Agent 回答及评测的完整工程闭环。取舍是优先验证核心链路，一些多人协作、完整回放和大规模性能能力仍未完成。

#### 深挖追问与证据

- 追问：最能代表个人贡献的三个模块？可选择 Wiki/RAG、Agent Runtime、SDD + Harness，并准备具体文件和 Bug 案例。
- 追问：AI 工具参与多少？如实说明使用方式，重点落在你做的决策、验证和结果责任。
- 证据：提交记录、设计文档、测试、评测报告和可运行链路，而不是只列技术栈。

### 4. 最大的技术决策是什么？

#### 20 秒直接回答

最大的决策是把原始资料和 Wiki 页面定义为可检查的知识源，把 FTS 和向量索引定义为可重建的派生数据。这样回答能沿引用回到来源，检索后端也能替换；代价是文件、FTS、向量和生命周期状态之间的一致性更复杂。

#### 60 秒 STAR/取舍版本

- **S**：如果把向量库当成唯一事实源，数据难以人工检查，模型或索引变化也会放大迁移风险。
- **T**：保证知识可以核验、修订，并允许检索实现演进。
- **A**：保留原始资料，生成可读 Wiki 页面；FTS 和向量只保存用于召回的派生表示，并通过文档身份与内容 hash 关联。
- **R**：实现了来源回溯和向量后端替换空间；代价是摄入后需要协调多种状态，而且跨存储无法天然获得单事务一致性。

#### 深挖追问与证据

- 追问：事实源到底是原文还是 Wiki？原文是最终核验依据，Wiki 是可维护知识层；两者都比索引更接近事实源。
- 追问：为什么不只保留原文？结构化页面提高复用和可编辑性。
- 证据：FTS/向量可以重建；回答引用可以回到页面和原始资料。

### 5. Node API 服务层和 Electron 主进程怎么分工？

#### 20 秒直接回答

Node 服务层负责业务逻辑和数据访问；Electron 主进程负责窗口、系统文件能力、生命周期和 IPC 适配。普通端点通过 Endpoint Registry 复用业务定义，同时生成 HTTP 和 IPC 入口。当前模糊点主要在流式传输和运行时组装，后续应继续把 HTTP、IPC、SSE 压薄为适配层。

#### 60 秒 STAR/取舍版本

- **S**：同一套业务既要支持 Web HTTP，也要支持 Electron IPC，如果各写一套会产生重复和行为漂移。
- **T**：复用业务逻辑，同时保留不同传输方式需要的适配。
- **A**：把 Wiki、Agent 和数据库能力放在服务层，用声明式 Endpoint Registry 生成普通 HTTP/IPC 入口；Electron 只承接桌面系统能力和进程生命周期。
- **R**：大部分普通请求可以共用实现；SSE、IPC 流式消息和后台服务启动仍横跨多个入口，是下一步需要收敛的边界。

#### 深挖追问与证据

- 追问：有没有重复？核心业务不是完整复制，但流式事件、启动和清理存在双入口适配代码。
- 追问：理想边界？服务运行时提供统一命令和事件接口，HTTP/IPC 只做协议转换。
- 证据：`server/endpoints/`、Electron main/preload 和流式路由；面试前按当前分支复核路径。

### 6. 为什么选 SQLite？遇到过什么问题？

#### 20 秒直接回答

Mint 是本地单用户桌面应用，SQLite 能把关系数据、FTS5 和 `sqlite-vec` 放进一条本地链路，部署成本低。主要问题是单写者竞争，以及 Electron 打包时 `better-sqlite3`、`sqlite-vec` 的原生 ABI 和动态库路径；WAL 和 `busy_timeout` 只能缓解写锁，不能消除约束。

#### 60 秒 STAR/取舍版本

- **S**：项目需要本地持久化、全文搜索和向量召回，又不希望用户额外部署数据库。
- **T**：用尽量少的运行依赖完成本地知识链路。
- **A**：选择 SQLite 保存业务数据和 FTS5 索引，默认用 `sqlite-vec` 保存向量；开启 WAL 和 `busy_timeout` 缓解读写等待。
- **R**：本地部署和备份简单，适合当前负载；代价是并发摄入时存在单写者瓶颈，Electron 跨平台打包还要处理原生模块兼容。

#### 深挖追问与证据

- 追问：WAL 是否解决并发写？没有，SQLite 仍然只有一个写入者。
- 追问：何时迁移 PostgreSQL？多人共享、并发写、权限过滤和跨实例运行成为真实需求时。
- 证据：数据库初始化配置、迁移和打包配置；不要把未做的规模压测说成结论。

### 7. 如果转向多人共享、支持多用户，你会怎么设计？

#### 20 秒直接回答

我会先把服务端变成共享数据的权威来源，建立组织、知识空间、成员和权限模型，并让权限过滤在检索阶段就生效。关系数据优先评估 PostgreSQL，向量可先评估 pgvector，文件进对象存储，摄入由持久化队列处理；SQLite 则退到客户端缓存或离线草稿。

#### 60 秒 STAR/取舍版本

- **S**：当前架构针对本地单用户，不能直接承担多租户权限、并发写和跨实例任务。
- **T**：在不泄漏知识的前提下支持共享、异步摄入和水平扩展。
- **A**：服务端建立租户和 ACL；检索前做权限过滤，引用返回前再次校验；文件进对象存储，任务进入可恢复队列，AgentRun 状态持久化并跨实例发布事件。
- **R**：设计上能支撑多人协作，但复杂度会显著上升。我的原则是先以 PostgreSQL/pgvector 验证统一存储边界，再根据数据量决定是否拆分专用向量服务。

#### 深挖追问与证据

- 追问：为什么权限必须在检索前？检索后再过滤可能已把无权内容送入模型或日志。
- 追问：如何处理离线编辑冲突？需要版本号、同步协议和明确冲突策略，当前尚未实现。
- 证据：这是演进设计，不应描述成现有能力。

## 二、知识库与检索

### 8. 用什么 Embedding 模型？Chroma 和 sqlite-vec 分别做什么？

#### 20 秒直接回答

默认是 BGE-M3、1024 维，通过 OpenAI 兼容接口调用；模型和地址可配置，但当前向量链路固定为 1024 维。FTS5 做关键词召回，`sqlite-vec` 是默认语义向量后端；Chroma 是实验性的替换后端，两者不是同时各负责一段。

#### 60 秒 STAR/取舍版本

- **S**：知识检索既要覆盖准确术语，也要覆盖语义改写。
- **T**：在本地优先的前提下实现关键词和语义两路召回，并保留后端替换能力。
- **A**：用 FTS5 做 lexical recall，用 BGE-M3 生成 1024 维向量；默认写入 `sqlite-vec`，通过 `VectorStore` 接口提供实验性 Chroma 适配。
- **R**：默认链路部署简单，外部后端也可验证接口边界；代价是当前维度与 schema 耦合，切换模型需要迁移或重建索引。

#### 深挖追问与证据

- 追问：为何是 BGE-M3？适合作为多语言检索起点，但没有完成多模型横向基准。
- 追问：切换维度怎么办？需要新表/迁移并全量重建，不能把不同维度混存。
- 证据：Embedding 配置、向量表 schema、`VectorStore` 实现；面试前核对默认配置。

### 9. 为什么选择 Chroma，而不是其他外部向量库？

#### 20 秒直接回答

选择 Chroma 是为了验证外部向量库能否通过 `VectorStore` 接口替换，而不是因为基准证明它优于 Qdrant 或 Milvus。它的 collection API 覆盖当前需要的 upsert、query、get 和 delete，适合作为第一个实验适配器；目前不能称为生产选型。

#### 60 秒 STAR/取舍版本

- **S**：默认 `sqlite-vec` 适合本地，但我需要验证向量存储是否真正可替换。
- **T**：用较低成本实现一个外部后端，暴露接口抽象和一致性问题。
- **A**：选择 API 简单且覆盖基本 CRUD/查询能力的 Chroma，实现适配器和连接验证。
- **R**：证明了接口替换路径，但也暴露了外部存储在 hash 校验、部署和失败处理上的差异。由于没有做同语料基准，我不会把它描述成性能优选。

#### 深挖追问与证据

- 追问：为什么不选 Qdrant？没有业务证据证明现在需要更复杂的过滤和运维能力。
- 追问：连接成功是否代表可用？不代表质量、延迟和故障恢复已经通过生产验证。
- 证据：适配器支持的操作和实验开关；明确“实验性”。

### 10. 加权 RRF 的权重怎么定？做过对照吗？

#### 20 秒直接回答

当前 legacy 公式是 `0.6/(60+关键词排名) + 0.4/(60+向量排名)`。关键词略高是工程先验，因为精确术语更稳定，向量用于补充语义改写；0.6/0.4 和 `k=60` 都没有经过正式离线调参，也没有完成朴素 RRF、加权求和的系统对照。

#### 60 秒 STAR/取舍版本

- **S**：BM25 与向量距离的原始分数尺度不同，直接相加不稳定。
- **T**：用简单、可解释的方法融合两路排名。
- **A**：采用基于名次的 RRF，未命中的一路贡献 0；基于术语命中更稳定的经验，把 lexical/vector 权重设为 0.6/0.4。
- **R**：避免了原始分数归一化问题，并通过排序测试保证实现一致；但权重只是启发式，不能宣称最优，下一步应在固定评测集上做消融。

#### 深挖追问与证据

- 追问：为何乘 1000？仅维持历史分数量级，不改变排序。
- 追问：如何做消融？固定语料、候选数和查询，比较 Recall@k、MRR/nDCG、答案通过率和延迟。
- 证据：融合公式和排序测试；明确没有正式 ablation。

### 11. Wiki 健康诊断检查什么？矛盾知识怎么处理？

#### 20 秒直接回答

`wiki_lint` 检查 frontmatter、必填字段、Schema 标签、断链、未编译资料、manifest/页面不一致、索引漂移和孤立页面。矛盾处理目前只做到候选冲突：同一 normalized key 下文本不同会标成 `contested`，但系统不会自动判定谁对，也没有把冲突状态完整带入回答。

#### 60 秒 STAR/取舍版本

- **S**：知识库长期演进后，结构错误、断链、索引漂移和内容冲突都会降低可信度。
- **T**：先把可确定检查的问题自动化，再对语义冲突保持保守。
- **A**：实现结构和一致性 lint；Claim 生命周期对相同 key 的不同文本记录 `contested/contradicted` 事件。
- **R**：能发现一批工程性健康问题和冲突候选；代价是没有通用近重复或事实裁决能力，当前回答也不保证主动提示冲突。

#### 深挖追问与证据

- 追问：孤立页面是什么意思？没有入链且不在索引中的 Wiki 页面，不是知识图谱实体。
- 追问：如何裁决冲突？需要来源等级、时间、人工确认或独立事实核查，不能只靠文本不同。
- 证据：lint 检查项和 Claim 事件定义。

### 12. 增量摄入时，旧 FTS 和向量怎么同步？

#### 20 秒直接回答

页面变化时，搜索文档和 FTS 在 SQLite 事务中替换；向量再按文档 ID、模型、维度和内容 hash 增量生成。SQLite 查询会校验向量 hash，避免旧向量冒充新内容。两者不是一个原子事务，所以短时间可能只有 FTS；Chroma 目前也缺少同等级的当前 hash 联查保护。

#### 60 秒 STAR/取舍版本

- **S**：重新摄入后，FTS 与向量更新速度不同，旧向量可能污染结果。
- **T**：让变化内容增量更新，并在失败时保持可用和可观察。
- **A**：事务内替换搜索文档/FTS；通过内容 hash 跳过未变向量，查询时校验当前 hash；Embedding 失败则保留 FTS，并记录失败状态供重试。
- **R**：SQLite 路径能避免大部分陈旧向量问题并支持降级；代价是跨阶段仍有覆盖缺口，外部 Chroma 的一致性保证更弱。

#### 深挖追问与证据

- 追问：为何不做分布式事务？成本与当前本地场景不匹配，采用状态机、幂等和可重试更现实。
- 追问：删除如何处理？需要按文档身份同步删除两类索引，并验证残留。
- 证据：事务边界、内容 hash、失败状态和重试入口。

### 13. 检索证据本身错误，会不会“有来源地胡说”？

#### 20 秒直接回答

会。引用只能证明答案用了哪份资料，不能证明资料本身真实。Mint 能做的是保留原文、验证证据片段来源、记录部分过期或冲突状态，让错误更容易被发现和修正；它没有完成全面事实核查，因此我不会说它解决了幻觉。

#### 60 秒 STAR/取舍版本

- **S**：RAG 常被误解为“有引用就正确”，但错误、过期或互相矛盾的来源仍会产生有出处的错误答案。
- **T**：提高可核验性，同时准确表达系统保证边界。
- **A**：保留来源归档和引用身份，检查证据片段来自原文，并记录部分生命周期和冲突信号。
- **R**：系统减少了一部分无依据生成，也让问题更容易定位；但没有独立核实所有来源，冲突状态尚未完整进入回答决策。

#### 深挖追问与证据

- 追问：怎样进一步改进？来源可信度、时效策略、冲突展示、主张—证据语义校验和人工反馈闭环。
- 追问：grounding 证明什么？证明引用身份来自本轮检索，不证明主张被语义支持。
- 证据：引用验证逻辑和 Claim 生命周期边界。

### 14. 检索覆盖率、引用覆盖率和引用 grounding 有什么区别？

#### 20 秒直接回答

检索覆盖率看要求的来源、chunk 和最低数量是否进入检索结果；引用覆盖率看答案引用是否满足用例断言；引用 grounding 看答案里的引用 ID 能否在本轮检索结果中找到。三者都不等于“答案语义被证据证明”。

#### 60 秒 STAR/取舍版本

- **S**：如果把不同检查都叫“证据匹配率”，很容易把身份一致误报成事实正确。
- **T**：把检索、生成引用和引用身份三个阶段分别测量。
- **A**：评测器分别检查 retrieval expectations、answer citation expectations 和 citation-to-retrieval identity。
- **R**：失败可以定位到召回、答案引用或引用伪造；代价是仍缺少对每个主张是否真正被证据支持的完整语义判定。

#### 深挖追问与证据

- 追问：为什么“100% grounding”不等于正确？它只检查引用 ID 的集合关系。
- 追问：应该怎样命名？“引用来源身份与检索结果一致率”更准确。
- 证据：评测断言字段和具体失败样例。

## 三、Agent Runtime 与韧性

### 15. 你提到韧性治理，具体做了哪些工作？

#### 20 秒直接回答

我把治理放在 ReAct 执行关口：调用前做 schema、权限和风险检查；执行时限制轮数、超时和重试；高风险操作进入审批；AgentRun 记录生命周期事件并推送状态。进程中断且工具结果未知时默认不重放，避免重复副作用。

#### 60 秒 STAR/取舍版本

- **S**：Agent 会调用外部工具，失败可能来自参数、权限、网络或进程中断，简单自动重试会放大副作用。
- **T**：限制失控、保留诊断证据，并提供安全恢复路径。
- **A**：在 ToolExecutor 前后增加校验、策略、审批、超时和有限重试；用 AgentRun 记录轮次、工具和终态事件；未知结果按 fail-closed 处理。
- **R**：失败不再只是聊天框里的一段文本，运行状态可以观察和处理；但这不是完整的跨进程续跑系统，事件回放和取消仍有缺口。

#### 深挖追问与证据

- 追问：哪些错误不能重试？参数、权限、配置错误和未知副作用操作。
- 追问：fail-closed 的代价？可能需要用户人工确认，但比重复执行外部动作安全。
- 证据：工具策略、审批状态、AgentRun 终态和恢复动作。

### 16. 工具调用应该重试、放弃，还是升级给用户？

#### 20 秒直接回答

判断标准是错误是否可能恢复、操作是否幂等、预算是否允许。网络暂时错误且可安全重复时可以重试；参数、权限、工具不存在等确定性错误应直接返回；高风险或结果未知的副作用操作应升级给用户。当前还有一个实现缺口：部分工具把失败包装成正常结果，外层 retry 不一定真正触发。

#### 60 秒 STAR/取舍版本

- **S**：统一重试策略会让不可恢复错误浪费预算，也可能重复执行副作用。
- **T**：按错误语义和幂等性决定恢复动作。
- **A**：配置 `toolMaxRetries`，外层采用指数退避；策略层区分校验、权限和审批。但实际 ToolExecutor 常把失败作为结构化结果 resolve，导致外层只看 Promise rejection 的 retry 覆盖不完整。
- **R**：模型仍可读取错误后改选方案，但“默认 5 次重试”不能理解为所有失败都重试 5 次。后续需要统一错误分类和 retry contract。

#### 深挖追问与证据

- 追问：默认参数？重试默认 5、范围 0–10，退避基数 1 秒、封顶 16 秒；面试前按当前分支复核。
- 追问：如何修？使用显式的 retryable error/disposition，而不是依赖 reject/resolve 语义。
- 证据：重试包装器与 ToolExecutor 返回协议的交界。

### 17. “调用预算”按什么计？超预算怎么办？

#### 20 秒直接回答

当前主要按工具调用次数计，策略支持总调用数、单工具数和单轮单工具数；ReAct 默认最多 5 轮、设置上限 20 轮。预算超限时拦截工具并要求基于已有信息回答。Token 会记录，但目前没有统一的每次运行 Token 或金额硬上限。

#### 60 秒 STAR/取舍版本

- **S**：Agent 循环可能因重复调用造成延迟、费用或外部风险。
- **T**：给运行设置可解释、可执行的停止边界。
- **A**：运行策略可限制总工具调用、单工具调用和每轮调用；ReAct 还有最大轮数。超限不再执行工具，而把状态交还模型收敛答案。
- **R**：能阻止部分无限循环，但生产聊天路径尚未统一启用完整工具预算，Token/金额预算也只是记录而非硬限制。

#### 深挖追问与证据

- 追问：轮数和调用次数有什么区别？一轮可能包含多个工具调用，必须分别约束。
- 追问：为什么评测显式传预算？用于验证策略，不代表所有生产路径默认相同。
- 证据：运行策略接口、默认轮数和预算测试。

### 18. 工具权限怎么落地？举一个拦截例子。

#### 20 秒直接回答

调用前依次检查工具是否注册启用、输入 schema、工具权限，再根据元数据、参数和资源路径做策略判断。例如 `http_fetch` 请求 `127.0.0.1` 会因回环地址被拒绝，不进入网络执行；公网 POST 等外部副作用则要求用户审批。

#### 60 秒 STAR/取舍版本

- **S**：模型生成的工具参数不能直接视为可信输入，尤其可能访问内网、越界路径或执行高风险命令。
- **T**：把权限控制放在确定性执行边界，而不是依赖 prompt 自律。
- **A**：注册与 schema 校验后，策略层检查 HTTP 目标、Bash 工作目录和路径、高风险命令与副作用类型；需要时暂停并请求审批。
- **R**：即使模型建议危险操作，执行器仍能阻断；代价是策略需要持续维护，并防范 DNS rebinding、符号链接等绕过方式。

#### 深挖追问与证据

- 追问：为什么 prompt 不够？模型输出不具备安全边界的确定性。
- 追问：审批是否等于安全？不是，审批要展示具体动作、目标和风险，执行层仍需限制范围。
- 证据：`toolPolicy` 测试和具体拒绝结果；路径按当前分支复核。

### 19. AgentRun 事件模型是什么？SSE 丢事件怎么处理？

#### 20 秒直接回答

事件带 `runId`、可选 `conversationId`、递增 `sequence`、类型和载荷，覆盖轮次、工具、审批、答案和终态。前端能忽略重复或倒退序号，但 SSE 目前没有 `id:`/`Last-Event-ID` 回放，也不会补拉序号缺口，所以它是有序推送，不是可靠事件流。

#### 60 秒 STAR/取舍版本

- **S**：Agent 运行跨多个步骤，只有最终文本无法支持进度展示、审批和故障诊断。
- **T**：建立统一生命周期和单运行内的事件顺序。
- **A**：AgentRun 分配递增 sequence 并发布结构化事件，通过 SSE/IPC 推送；客户端丢弃重复或非递增事件，持久层保存最小生命周期信息。
- **R**：运行过程可观察，审批也能继续内存中的运行；但完整答案、思考、所有 chunk 和参数没有全部持久化，断线期间事件不会可靠重放。

#### 深挖追问与证据

- 追问：sequence 能否解决丢失？只能发现顺序，当前客户端甚至未完整处理 gap，不能替代回放。
- 追问：如何完善？持久事件日志、SSE id、按 last sequence 重连补拉、终态幂等。
- 证据：事件类型、持久化字段、SSE 序列化和客户端过滤逻辑。

### 20. 为什么选 SSE？用户取消怎么处理？

#### 20 秒直接回答

Agent 主流量是服务端向客户端推送，发送消息、审批和取消可以走普通 HTTP/IPC，因此 SSE 比 WebSocket 更简单。当前取消还不完整：客户端停止 fetch 不等于服务端 Agent 收到取消。完整方案应按 `runId` 提供幂等取消，并把 AbortSignal 贯穿模型和工具。

#### 60 秒 STAR/取舍版本

- **S**：消息生成和运行状态主要单向下发，控制操作频率低。
- **T**：用低复杂度协议支持流式回答，同时保留独立控制接口。
- **A**：Web 采用 POST 后读取 SSE，审批等动作走控制请求；Electron 用 IPC 适配事件。
- **R**：通信模型与业务方向匹配；但连接断开目前主要结束响应，Web/Electron 的 abort 没有统一传播到服务端执行链。

#### 深挖追问与证据

- 追问：何时更适合 WebSocket？高频双向协作、客户端持续上报或共享实时状态时。
- 追问：主动取消与断网为何要区分？断网可能需要后台继续，主动取消应终止模型/工具并产生唯一 `run_cancelled`。
- 证据：Web SSE 路由、IPC abort 和 AbortSignal 传播边界。

## 四、Jev 与语义决策

### 21. Jev 是什么？为什么不用通用 LLM JSON 或传统分类器？

#### 20 秒直接回答

Jev 是 TypeSafe 的 System One 判定接口，调用方用 state 和类型化问题请求 choice、score 或 noul。Mint 用它做候选选择、门控和相关性判断。通用 LLM JSON 也能做，Jev 的价值是减少自定义协议和解析；它不自动保证更准确，固定类别且有标注数据时传统分类器可能更合适。

#### 60 秒 STAR/取舍版本

- **S**：路由、记忆价值和 rerank 都是小型语义判断，如果每处自定义 prompt + JSON，会产生重复协议和解析失败。
- **T**：把判定问题类型化，限制输出空间，并提供统一失败回退。
- **A**：用 Jev 声明候选或分数问题，业务代码仍掌握候选集合、阈值、回退和最终执行。
- **R**：集成代码更结构化，也便于 fail-closed；代价是依赖外部服务，confidence 未必校准，质量仍需用任务数据验证。

#### 深挖追问与证据

- 追问：为什么不是 Agent 自己判断？小判定可减少大模型调用和自由输出，但是否更优需实测。
- 追问：Jev 能执行动作吗？不能，业务代码验证结果后决定动作。
- 证据：类型化问题、候选白名单、阈值和 fallback。

### 22. Agent 路由阈值怎么定？校准过吗？

#### 20 秒直接回答

默认最低置信度是 0.5，可配置到 0–1。低于阈值就拒绝 Jev 结果并走 legacy 路由。这个值是工程启发式，没有用独立人工标注集校准；Jev confidence 也不能直接当成已校准概率。

#### 60 秒 STAR/取舍版本

- **S**：无阈值会接受不确定路由，阈值过高又会导致大量 fallback。
- **T**：在错误专用 Agent 和回退通用路径之间建立保守边界。
- **A**：先设置 0.5 作为可配置起点，低于阈值不采用 Jev 选择；记录结果，计划用人工标注的路由集评估 coverage、accuracy 和分桶可靠性。
- **R**：当前机制能拒绝低置信结果，但尚不能证明 0.5 最优，也不能用 Judge 的其他校准结果替代路由校准。

#### 深挖追问与证据

- 追问：如何校准？构建独立标注集，画 reliability curve，按误路由成本选择阈值。
- 追问：阈值错的代价？过低选错专用 Agent，过高则丢失路由收益并增加回退。
- 证据：默认配置、拒绝与 fallback 分支；面试前按当前代码复核。

### 23. 记忆门控更担心漏记还是错记？

#### 20 秒直接回答

两者代价不对称：漏记会降低个性化，错记会把错误、过期甚至敏感信息带进后续回答，所以高风险类别更担心错记。历史实现的默认价值阈值是 0.4，而且 Jev 返回 `skip` 时不会再走 legacy；这部分正在随记忆域重构，面试前必须按目标分支复核。

#### 60 秒 STAR/取舍版本

- **S**：统一阈值无法同时适配长期偏好、临时上下文、敏感信息和用户纠正。
- **T**：在个性化收益与错误传播、隐私风险之间做分类取舍。
- **A**：历史实现以 0.4 为启发式阈值，Jev 不可用才 fallback；更合理的演进是按记忆类别设置不同准入、过期和确认策略，并提供查看、纠正和删除。
- **R**：现有门控提供了初步筛选，但没有完成类别化成本校准。当前仓库正在调整记忆边界，不应把旧目录和旧行为描述成稳定现状。

#### 深挖追问与证据

- 追问：什么必须显式确认？敏感信息、身份属性或高影响长期事实。
- 追问：如何评估？分别计算漏记/错记，按类别和下游伤害加权，而不是只看总体准确率。
- 证据：目标分支中的记忆策略、数据模型、删除能力和测试；不要只引用旧实现。

### 24. Jev 重排和 Cross-Encoder 比，效果和成本如何？

#### 20 秒直接回答

Mint 的 Jev rerank 是实验能力：先从 legacy 结果取有限候选，再做语义相关性判断，失败时回退。项目没有部署 Cross-Encoder，也没有同数据集对照，因此不能断言谁更好。比较时应看 nDCG/MRR、Recall@k、回答质量、P95 延迟和单次成本。

#### 60 秒 STAR/取舍版本

- **S**：RRF 能融合召回，但靠排名本身无法判断候选是否真正回答查询。
- **T**：验证类型化语义判断能否改善 top results，同时保持可回退。
- **A**：对有限候选使用 Jev rerank，外部服务失败则保留 legacy 排序；把 Cross-Encoder 视为待对照方案，而不是假设基线。
- **R**：建立了实验路径和降级能力，但尚无同候选集质量/成本基准。实现后来可能由逐项调用调整为批量判断，面试前必须核对当前版本，避免背旧链路。

#### 深挖追问与证据

- 追问：Cross-Encoder 的优势？通常可本地部署并直接对 query-document 对打分；代价是模型算力和运维。
- 追问：Jev 的成本？外部网络、服务费用和可用性；批量与逐项调用的延迟差异需实测。
- 证据：当前 rerank provider、候选数量、fallback 测试和最新评测报告。

## 五、RAG Eval 与指标

### 25. 评测集多大？谁出的？有无答案或对抗样本吗？

#### 20 秒直接回答

当前 `wiki-rag.json` 有 25 题、10 篇固定资料，每题跑 3 次，共 75 次运行；其中 3 道拒答题、1 道安全对抗题。题目和断言由我维护，没有独立双人标注或仲裁，所以它适合回归，不足以代表广泛真实分布。

#### 60 秒 STAR/取舍版本

- **S**：只凭几个成功演示无法判断 RAG 是否稳定，也无法定位检索、引用或工具策略失败。
- **T**：建立可重复的小型回归集，并保留逐次运行结果。
- **A**：基于 10 篇固定资料编写 25 个 case，加入来源、chunk、答案、拒答和工具断言；每题运行 3 次观察稳定性。
- **R**：得到 75 次可追溯运行并能分析间歇失败；限制是开发者自标、题量小、对抗覆盖有限，README 的题数也曾落后于 JSON。

#### 深挖追问与证据

- 追问：如何避免刷榜？冻结测试集、增加 blind set、独立标注、保留失败和版本化报告。
- 追问：1 道安全题够吗？不够，只能证明该样例行为，不能宣称系统安全。
- 证据：数据集文件、case ID、语料清单和报告版本。

### 26. Pass@3 和 Pass^3 怎么定义？

#### 20 秒直接回答

每题运行 3 次时，Pass@3 是至少一次通过的题目比例，Pass^3 是三次全部通过的题目比例。这里的 passed 是答案、检索、引用、拒答、工具策略等复合门槛，不是单纯语言质量分。

#### 60 秒 STAR/取舍版本

- **S**：生成式系统有波动，只看单次通过率既看不到“偶尔能成功”，也看不到稳定性。
- **T**：同时衡量能力上界和重复稳定性。
- **A**：每题重复三次；统计至少一次通过和全部通过，并保留逐次断言结果。
- **R**：Pass@3 高说明问题至少有成功路径，Pass^3 高才说明稳定；两者必须结合失败分布解读，不能拿 Pass@3 代替可靠性。

#### 深挖追问与证据

- 追问：与普通 pass rate 区别？普通 pass rate 以运行次数为分母，题级 Pass@3/Pass^3 以题目为分母。
- 追问：为什么不是纯答案评分？当前 `passed` 是复合工程门槛。
- 证据：指标计算代码、runsPerCase 和逐题结果。

### 27. Pass@3 和 Pass^3 相差 8 个百分点说明什么？

#### 20 秒直接回答

如果同一份 25 题报告是 96%/88%，题级含义是 24 题至少通过一次、22 题三次全过，也就是两题间歇失败、一题持续失败。但仓库没有这组报告：可追溯版本是 2026-09-22 的 96%/84% 和 2026-09-29 的 96%/80%，不能混用失败分布。

#### 60 秒 STAR/取舍版本

- **S**：百分比差值容易被直接归因于“模型随机性”，但失败可能来自检索、引用、工具或断言。
- **T**：把聚合指标还原到题级和逐次轨迹。
- **A**：先确认同一报告版本和分母，再分类间歇失败与持续失败，检查检索结果、引用和工具轨迹。
- **R**：最新可追溯报告中有 4 道间歇失败、1 道三次全失败；间歇失败主要与未生成引用有关，持续失败是 `security-001` 工具断言。这个结论只属于该报告。

#### 深挖追问与证据

- 追问：能否证明是模型波动？不能，必须看逐次组件结果。
- 追问：为什么强调报告版本？数据集、代码、模型和配置变化都会改变分母和失败原因。
- 证据：2026-09-22 与 2026-09-29 的版本化 JSON；不要使用无对应报告的 96%/88%。

### 28. RAG Eval 是自动还是人工？Judge 偏差怎么控制？

#### 20 秒直接回答

主通过率来自确定性检查；LLM/Jev Judge 是可选辅助，只评通过硬门槛且配置了 rubric 的结果，并单独记录，不改写 deterministic pass。项目有人工校准模板和一致率计算，但当前没有完整人类标签和校准结果，所以不能说 Judge 已校准。

#### 60 秒 STAR/取舍版本

- **S**：纯字符串断言难评语言质量，纯 Judge 又可能不稳定、偏置或掩盖硬错误。
- **T**：把确定性工程约束和主观质量判断分层。
- **A**：先运行来源、引用、拒答和策略断言，再对符合条件的样本按 rubric 调 Judge；结果分开存储，并预留人工标签对齐流程。
- **R**：硬门槛不会被 Judge 的高分覆盖，质量信号也能额外观察；限制是当前缺少独立人工校准，且 Judge 看到确定性结果可能产生锚定偏差。

#### 深挖追问与证据

- 追问：如何降低锚定？盲化部分输入、多人标注、分维度一致率和定期复核 disagreement。
- 追问：Judge 能否决定发布？当前不应单独决定，应与硬指标和人工抽检结合。
- 证据：judge rubric、结果字段、校准模板及缺失的人类标签。

### 29. 有没有看起来漂亮但意义有限的指标？

#### 20 秒直接回答

最典型的是“检索覆盖率 100%”。它只说明用例要求的来源或 chunk 被命中，不代表召回完整、排序合理，更不代表证据语义支持答案。我会把它叫“必需来源检查覆盖率”，并与 Recall@k、引用支撑和失败分布一起报告。

#### 60 秒 STAR/取舍版本

- **S**：单一百分比很容易被包装成系统准确率，尤其当测试集小且断言由开发者维护时。
- **T**：让指标名称和它实际验证的对象一致。
- **A**：拆分检索覆盖、答案引用、引用 grounding、拒答和 Judge，并在报告中附带分母、数据集与版本。
- **R**：指标更可解释，也更容易定位回归；代价是无法用一个数字概括全部质量，需要接受多指标和样例分析。

#### 深挖追问与证据

- 追问：Recall@k 应从哪里算？从有顺序的 `retrievedCitations` 算，不能从最终展示 citations 反推。
- 追问：100% 是否没有价值？有回归价值，只是不能扩大解释。
- 证据：指标定义、分母和具体 case 结果。

### 30. 面试官质疑 100% 指标是刷出来的，怎么自证？

#### 20 秒直接回答

我不会争辩这个数字代表普遍正确率，而会交付数据集、语料、运行配置、逐次结果和计算代码，让对方随机抽题复算或在干净 Wiki 上重跑。同时说明 100% 只属于特定检查、特定版本和小型数据集，所有失败都应保留。

#### 60 秒 STAR/取舍版本

- **S**：开发者自己出题、调系统，很容易对测试集过拟合。
- **T**：让结果可复现，并限制指标外推范围。
- **A**：版本化语料、数据集和报告；记录模型、运行次数、断言和逐次轨迹；支持隔离环境重跑，并公开失败样例。
- **R**：别人可以验证计算和具体行为，但这仍不能消除样本选择偏差。下一步需要 blind set、独立标注和更广泛真实查询。

#### 深挖追问与证据

- 追问：如果重跑下降怎么办？保留新结果并分析环境、模型和链路变化，不挑最好的一轮覆盖历史。
- 追问：如何防止改题迎合结果？数据集版本化、评测代码评审、冻结集和外部样本。
- 证据：报告版本 ID、dataset hash/版本、逐次结果和计算实现。

## 六、SDD、规模与复盘

### 31. SDD 闭环最痛的一环是什么？举一个真实 Bug。

#### 20 秒直接回答

最痛的是验证真实状态时序，而不是让 mock 通过。一次真实 Bug 是首条消息先创建会话，随后运行失败，但失败 setter 仍绑定空会话 ID，导致错误写到错误目标。修复后又发现同 URL 的两条 SSE mock 后注册覆盖前一条，原来的失败场景其实没测到。

#### 60 秒 STAR/取舍版本

- **S**：首次连接模型时，会话创建和消息运行跨越多个异步状态；失败后用户应该在新会话里看到错误并重试。
- **T**：保证失败状态写入正确会话，并让验收场景真正执行失败分支。
- **A**：我让 setter 显式接收目标 conversation ID，增加类型和浏览器失败场景；随后排查出重复 SSE mock route 的覆盖问题并修正 mock。
- **R**：用户能在正确会话看到失败状态，测试也从“看似通过”变成真正覆盖目标分支。这个案例说明 SDD 的 AC 必须绑定可观察行为和真实时序。

#### 深挖追问与证据

- 追问：为什么单测没发现？单元 mock 没复现会话 ID 从空到新建的状态转换。
- 追问：如何防止假验收？检查 mock 命中次数、失败响应和 UI 最终状态，不能只看脚本退出码。
- 证据：对应变更的 AC、浏览器场景、失败前后截图/日志和测试。

### 32. 项目最让你担心的问题是什么？解决了吗？

#### 20 秒直接回答

最担心的是答案有来源，但来源本身错误、过期或矛盾。Mint 通过来源归档、引用和部分冲突生命周期提高可核验性，但没有完成全面事实核查，冲突状态也未完整进入回答决策，所以这个问题只被缓解，没有被解决。

#### 60 秒 STAR/取舍版本

- **S**：RAG 会把“无来源幻觉”转化为“有来源但来源不可靠”的风险。
- **T**：让系统的可信边界可见，并逐步形成纠错闭环。
- **A**：保留原文和引用身份，检查证据片段来源，记录部分过期/冲突信号，同时在评测中区分 grounding 与事实正确。
- **R**：用户更容易定位和修正错误，系统也能减少部分无依据回答；但来源真实性、冲突裁决和时效性仍需要人工和更强验证能力。

#### 深挖追问与证据

- 追问：为什么仍值得做？可追溯错误比不可定位错误更容易治理，但不能把“可治理”说成“已正确”。
- 追问：下一步优先级？先把冲突/过期状态展示给检索和回答，再做主张—证据核验与反馈回流。
- 证据：来源链、Claim 状态和当前未覆盖边界。

### 33. 如果数据量扩大 10 倍，哪个模块先遇到瓶颈？

#### 20 秒直接回答

我最先担心摄入后扫描全 Wiki 和重建索引，它会随全库增长并加重 SQLite 写压力。改法是让摄入明确产出增删改清单，只更新对应 FTS；向量生成改成持久化、可恢复的批任务，再用真实 10 倍语料压测后决定是否拆存储。

#### 60 秒 STAR/取舍版本

- **S**：当前本地规模下全库扫描可接受，但 10 倍页面和 chunk 会放大扫描、Embedding 和写锁成本。
- **T**：把工作量从“随全库增长”改成“随本次变更增长”。
- **A**：摄入阶段生成 change set；FTS 按文档增量更新；向量任务按内容 hash 幂等、持久化并可恢复；监控写锁等待、队列积压和查询 P95。
- **R**：预期能显著降低重复工作，但是否需要迁出 SQLite 必须由压测决定，不能只凭数量级做架构升级。

#### 深挖追问与证据

- 追问：10 倍到底是什么？要澄清文档数、chunk 数、单文档大小、查询并发还是摄入频率。
- 追问：首先观测哪些指标？摄入 wall time、锁等待、Embedding 吞吐、积压恢复时间、P50/P95 查询延迟。
- 证据：当前全库扫描路径与增量 hash 机制；未来设计不冒充已实现。

### 34. 哪些是“够用就行”的妥协？哪些必须坚持？

#### 20 秒直接回答

SQLite、FTS 优先、向量异步补齐和暂不分布式，都是可随规模演进的妥协。不能妥协的是数据身份、来源不断链、失败状态可见，以及不能因为重试而重复副作用。可以暂时吞吐不高，但不能静默给出错误状态。

#### 60 秒 STAR/取舍版本

- **S**：个人项目资源有限，如果所有能力按企业级设计，会被基础设施拖垮。
- **T**：区分可逆技术选择和不可逆的可信边界。
- **A**：在可替换存储和性能能力上采用简单方案；在来源身份、状态记录、幂等和风险审批上建立硬约束。
- **R**：项目能快速验证核心价值，同时保留演进空间。取舍标准不是“是否高级”，而是失败后是否可发现、可解释、可恢复。

#### 深挖追问与证据

- 追问：如何判断可逆？是否能通过接口、迁移或重建替换，而不破坏用户知识和运行语义。
- 追问：向量短时缺失能否接受？可以，但必须状态可见、可重试并安全降级到 FTS。
- 证据：索引可重建、失败状态、工具幂等和来源身份设计。

### 35. 如果从头重做，哪三个设计会改？

#### 20 秒直接回答

第一，从第一版就把摄入和索引做成增量、持久化、可恢复流水线；第二，先定义完整的 AgentRun 取消、回放和终态协议；第三，尽早建立版本化、有人审记录的评测集。这三项分别解决规模、运行中断和可信评测，越晚补迁移成本越高。

#### 60 秒 STAR/取舍版本

- **S**：项目演进后，最贵的问题不是单个功能，而是早期基础边界不足导致的跨模块补课。
- **T**：找出最值得前置的三类基础能力。
- **A**：摄入以 change set 和持久任务为中心；AgentRun 先定义 cancel/replay/terminal invariants；评测从一开始记录数据来源、版本、人工复核和失败样例。
- **R**：这些设计会增加第一版成本，但能减少后续全库重扫、断线不可恢复和指标不可比较的问题。我不会一开始就做微服务或复杂分布式，因为它们没有同样明确的早期收益。

#### 深挖追问与证据

- 追问：为什么当初没这样做？早期优先验证端到端价值，真实问题在运行和评测中才显现。
- 追问：这是不是过度设计？只前置协议和数据边界，具体基础设施仍按规模渐进实现。
- 证据：当前摄入扫描成本、SSE/取消缺口、历史报告版本差异和失败复盘。
