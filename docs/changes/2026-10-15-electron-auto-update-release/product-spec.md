# Electron 自动更新与版本发布规格

## 背景与目标

Mint Electron 当前可以生成 macOS DMG，但没有自动更新器或正式发布流水线。多个第一方 workspace 的版本号也不一致。目标是从 `0.1.0` 开始统一产品版本，并让已安装的 macOS 应用能够检查、下载和安装后续版本。

## 用户与场景

- Mint 桌面应用用户希望不必手动查找并下载每个新版本。
- 维护者希望用一个可审查的 GitHub Release 流程生成并发布安装包和更新元数据。

## 用户故事

- **US-001**：作为 Mint 用户，我希望应用自动发现并下载新版本，并在合适时机安装，以便持续使用受支持的版本。
- **US-002**：作为维护者，我希望通过带版本号的发布流程构建经过检查的安装包，以便可靠发布更新。
- **US-003**：作为开发者，我希望开发模式可显式连接本机更新源，验证检查和下载流程，而不连接正式 Release。
- **US-004**：作为 Mint 用户，我希望在设置的“关于”页查看当前版本并手动检查更新，以便确认更新状态。

## 范围

### 功能需求

- **FP-001**：首发产品版本为 `0.1.0`。根项目及所有第一方 workspace 包的 `version` 字段统一为 `0.1.0`；新版本遵循 SemVer。
- **FP-002**：已打包的 macOS 应用在启动后检查 GitHub Releases 上的更新，并在后台自动下载可用更新。开发模式默认不检查更新；本机测试例外见 FP-007。
- **FP-003**：下载完成后在 Mint 主界面显示更新提示，提供“现在重启”和“忽略此版本”选择。忽略选择按版本保存，不再提示该版本；发现更高版本时继续提示。更新只在用户选择重启后安装，安装前需完成本地 Server 的优雅关闭。
- **FP-004**：更新检查或下载失败时，当前应用继续运行并记录不含凭据的诊断信息。
- **FP-005**：以 `v<version>` Git tag 触发 macOS 发布构建。流水线构建 DMG、ZIP 和更新元数据，检查版本与 tag 一致，并上传到 Draft GitHub Release；维护者审阅后发布 Release。
- **FP-006**：发布脚本或 CI 校验所有第一方 workspace 的版本号与根 `package.json` 一致。
- **FP-007**：仅在未打包的开发应用中，设置 `MINT_ENABLE_LOCAL_UPDATE_TESTS=1` 且 `MINT_LOCAL_UPDATE_URL` 指向 loopback HTTP 地址时，才连接本机 Generic 更新源。测试更新下载完成后显示 Mint renderer toast，展示与正式更新相同的界面；安装按钮禁用，开发模式不执行安装或关闭 Server。
- **FP-008**：日志记录更新源模式、检查开始、发现更新/无更新和下载完成的版本号；不记录完整 feed URL、凭据或下载进度明细。
- **FP-009**：设置窗口提供“关于”页，显示当前应用版本和“检查更新”操作。手动检查当前已配置的更新源；有更新时后台下载并在下载完成后显示 Mint 更新提示，无更新和失败时显示对应状态。开发模式未启用本地测试源时，显示不可检查原因。

### 业务规则

- **BR-001**：Git tag 去掉 `v` 前缀后，必须等于根 `package.json` 的版本号。
- **BR-002**：只有正式打包的应用连接 GitHub 更新源；开发构建默认不检查，显式测试模式只能连接 BR-005 允许的 loopback 源。
- **BR-003**：应用不得因更新检查失败而退出，也不得自动强制重启用户正在使用的应用。
- **BR-004**：私钥、Apple 凭据和 GitHub 写入令牌只能来自 CI Secrets 或签名环境变量，不得写入仓库或安装包。
- **BR-005**：本地测试源只允许 `localhost`、`127.0.0.0/8` 或 `::1` 的 HTTP URL；远端、带凭据、query 或 fragment 的 URL 均拒绝。

## 验收标准

- **AC-001**（风险：中）：所有第一方 workspace 的版本字段为 `0.1.0`，版本一致性检查通过；tag `v0.1.0` 被接受，版本不匹配的 tag 被拒绝。可验证不变量：所有第一方 workspace 的 `version` 均等于根版本。最低证据：自动化检查。
- **AC-002**（风险：高）：打包应用启动时会检查 GitHub 更新并下载新版本；开发模式默认不访问更新源。可验证不变量：GitHub 源只在 `app.isPackaged` 时使用，开发源需满足 AC-007。最低证据：Updater 单元测试和 Electron 进程级冒烟。
- **AC-003**（风险：高）：下载完成时 Mint 主界面显示提示，用户可以选择立即重启安装或忽略当前版本；忽略状态跨应用重启保留，新版本仍可提示。安装只由用户明确操作触发，且 Server 已完成关闭后才安装。可验证不变量：忽略的版本不会在退出时自动安装；安装动作不绕过 Server shutdown。最低证据：更新器生命周期测试、提示持久化测试和 Electron 进程级冒烟。
- **AC-004**（风险：高）：更新检查、下载和安装出错时，现有应用可继续工作，日志不包含凭据，下载 Promise 不产生未处理拒绝。可验证不变量：失败路径不调用退出或安装；日志中不出现密钥；自动下载失败有 rejection handler。最低证据：Updater 单元测试和日志断言。
- **AC-005**（风险：高）：`v0.1.0` 发布流水线生成 DMG、ZIP、更新清单及校验元数据，并将产物附加到 Draft Release；tag 与产物版本匹配。可验证不变量：发布只使用符合 BR-001 的 tag。最低证据：macOS 构建产物检查及流水线静态检查。
- **AC-006**（风险：中）：没有配置发布签名凭据时，CI 明确失败或只运行非发布验证，不得发布无法自动更新的正式产物。可验证不变量：未签名包不会进入正式 Release。最低证据：发布配置静态检查及 CI 条件验证。
- **AC-007**（风险：中）：开发模式默认不检查更新；只有显式开关和 loopback 更新源都有效时才检查并下载。下载完成后显示 Mint renderer toast，安装按钮禁用，不调用 `quitAndInstall` 或 Server shutdown。可验证不变量：默认关闭、拒绝非本机源、开发下载不安装。最低证据：Updater 单元测试和浏览器场景。
- **AC-008**（风险：低）：更新日志能区分禁用、local-test/GitHub 源、检查开始、更新可用/无更新和下载完成；日志不包含完整 URL 或凭据。可验证不变量：关键阶段都有版本/来源日志，敏感字符串已脱敏。最低证据：Updater 单元测试。
- **AC-009**（风险：中）：关于页显示 Electron 当前版本，用户可手动检查当前更新源；界面区分最新、发现更新、未启用更新源和检查失败。可验证不变量：手动检查只访问 configureAutoUpdater 已启用的源；发现更新仍使用自动下载和已有更新提示流程。最低证据：Updater IPC 单元测试和浏览器场景。

## 非目标

- Windows、Linux 自动更新。
- 不重启应用的 JavaScript/资源热替换。
- 本次发布真实 `v0.1.0` 到 GitHub 或配置真实 Apple Developer 账号与证书。
- 数据库 schema 或用户数据迁移。
- 在开发模式安装测试更新包；真实安装由打包应用验证。

## 依赖与风险

- macOS 自动更新依赖一致的代码签名身份；公证也需要 Apple Developer 凭据。
- GitHub Release 作为公开更新源。实际仓库可见性及访问策略仍需在首次发布前确认。
- 本地验证可以证明打包内容和更新逻辑；只有配置签名凭据并发布真实 Release 后，才能验证用户设备上的完整更新链路。
