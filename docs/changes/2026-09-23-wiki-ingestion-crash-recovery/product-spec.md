## 背景与目标

Wiki 摄入已经把输入文件写入暂存目录，并将作业持久化到 SQLite。启动时，处理中作业会重新排队。但单次摄入还会依次写 Markdown 页面、Source/Page/Claim 生命周期记录、搜索索引、图谱和 manifest；进程可能在任一步骤后退出。当前作业重放会重新调用编译器，不能证明重放不会生成重复版本、重复 manifest/生命周期事件，或因暂存文件已移动而失去输入。

本变更面向**已持久化的摄入作业**，为提交阶段提供可恢复、幂等的执行记录：发生异常退出后，启动恢复应继续完成同一批已编译结果，且不会重复产生可观察的知识数据。

## 用户与场景

- 用户上传 Wiki 文件或从 Chat 发起多资料摄入。
- 服务在 LLM 编译期间或提交页面、Source、索引、manifest 期间被强制终止。
- 服务重启后自动恢复作业，最终用户只看到该作业完成一次，或收到可诊断的失败状态。

## 范围

### 本次做

- 为作业中的每个摄入单元保存稳定的提交身份及编译快照，使提交重放不依赖再次调用 LLM。
- 为 Source 路径、页面写入、生命周期注册、搜索索引和 manifest 建立可重复执行的提交边界。
- 在启动恢复时继续未完成的提交，并在已完成的提交上安全短路。
- 覆盖上传单文件与 Chat 多文件；多文件项仍各自隔离。
- 通过进程级故障注入/强制退出验证重启后的真实恢复路径。

### 本次不做

- 多进程/分布式 worker 租约和跨主机协调。
- 任务 dead-letter、通用重试策略或 LLM 错误分类；LLM 调用发生在编译快照之前，不属于提交重放。
- 清理所有历史暂存孤儿或提供新的运维 UI。
- 保证文件系统、SQLite、外部向量库构成一个原子事务；要求以持久提交记录向前恢复，并确保每步可幂等重放。
- 改变知识编译、证据校验、页面冲突策略和用户可见 API 契约。

## 业务规则

- **BR-001**：本规格只承诺已在 SQLite 中创建的摄入作业。作业创建前的暂存孤儿清理不在范围内。
- **BR-002**：LLM 编译成功后，应先持久化足以重放提交的完整快照，再开始提交副作用。
- **BR-003**：同一作业项的提交身份在重启和重试中保持稳定；同一副作用重放不得新增重复版本、事件或 manifest 项。
- **BR-004**：提交一旦进入可恢复阶段，恢复策略向前完成，不以重新编译不同输出覆盖原快照。
- **BR-005**：Chat 多文件作业中，一个条目恢复失败不能回滚其他已成功条目。
- **BR-006**：旧任务 payload 中指向正式 `sources/...` 的路径继续兼容，不得误删用户已有文件。

## 验收标准

- **AC-001（P0）**：在编译快照持久化后、提交各副作用前后强制结束进程，重启 worker 后作业可继续完成；恢复提交不再次调用 LLM。
- **AC-002（P0）**：重复恢复同一作业项不会增加重复 Source/Page 版本、Claim 支持计数/事件或 manifest 条目；正式 Source 文件恰有一份。
- **AC-003（P0）**：恢复完成后 Markdown 页面、生命周期库、搜索索引和 manifest 均能指向同一稳定提交结果；提交已完成时重复 drain 不产生写入副作用。
- **AC-004（P0）**：真实子进程退出测试能够在提交中途终止执行，随后由新进程读取同一数据库/Wiki 目录恢复；探针验证最终状态与上述不变量，而非仅验证启动命令退出码。
- **AC-005**：Chat 多条目作业在其中一条提交中途退出后，各条目按稳定身份分别恢复，已完成项不重做、不被失败项回滚。
- **AC-006**：现有暂存输入、旧 `sources/...` payload 和普通成功/失败路径保持兼容；证据校验失败仍不得把失败内容提交为正式 Source。

## 风险与依赖

- 文件系统与 SQLite 无法共享原子事务；恢复依赖明确的提交阶段记录和副作用幂等性。
- 向量索引可能使用外部服务；本期以可重复 upsert/同步并验证 FTS/生命周期主数据为准，不承诺远端向量库的事务原子性。
- 进程级故障探针必须只存在于测试注入边界，不得暴露为生产环境可调用的故障开关。
- 实现前必须对摄入服务、作业恢复、页面编译/写入和生命周期注册做 GitNexus 影响分析；若索引不可用，记录降级原因并以源码调用链、定向测试及风险审查补充，不能把 UNKNOWN 当作低风险。
