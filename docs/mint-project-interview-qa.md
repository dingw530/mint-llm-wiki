# Mint 项目面试问答

整理日期：2026-09-29

## 一、产品动机与架构

### 1. 市面上已有 ima、Obsidian 等产品，为什么还要做 Mint？

我做 Mint 的起点是自己的使用痛点：资料越来越多，但“存下来”不等于以后能用。到了提问时，我既想找到相关内容，也想确认答案依据了哪些原始资料；知识还会持续变化，检索结果也需要能观察、能修正。

所以我希望把资料摄入、Wiki 整理、混合检索、带来源回答和运行观察连成一个工作流。Mint 的切入点比较窄，是验证个人、本地知识库能否做到可积累、可检索、可溯源。我不会把它说成要取代 ima 或 Obsidian，也不认为这些能力是其他产品原则上做不到的。

### 2. 为什么选择 Karpathy 的 LLM Wiki 方案？

我看中的是它把原始资料和整理后的 Wiki 页面分开：原始资料保留，模型负责辅助编译成有结构的页面，用户可以查看和修改，再从页面中检索。这样知识可以逐步沉淀，不必每次回答都从一批原始文件临时拼接。

它适合作为 Mint 的基础，是因为工作流简单、数据形式可见，而且和本地 Markdown 知识库契合。它并不会自动保证整理后的内容正确，所以 Mint 还需要来源追溯、证据检查和人工修订。

### 3. 这个项目是独立做的还是团队协作？你负责什么？

Mint 是我主导的个人项目。核心的产品方向、架构、前后端实现、Electron 集成、SDD 文档、Harness 和 RAG Eval 都是我推进的。

项目里使用了 SQLite、Embedding 服务和 Jev 等现有能力，我负责的是它们在 Mint 中的集成、业务链路和验证，不会把这些底层能力说成我从零开发的。

### 4. 最大的技术决策是什么？

如果只能选一个，我会说是把**原始资料和 Wiki 页面作为可检查的知识源，把 FTS 和向量索引作为可重建的派生数据**。这样回答可以沿引用回到来源，搜索后端也能替换；向量库不会成为唯一的知识事实源。

代价是摄入后要同步文件、FTS、向量和知识生命周期状态，跨存储的一致性也更复杂。这是我认为最重要的架构取舍：优先保证资料能被用户检查和修订，再优化检索能力。

### 5. Node API 服务层和 Electron 主进程怎么分工？有没有逻辑重复或边界模糊？

Node 服务层负责业务逻辑和数据访问，包括 Wiki、检索、Agent 和数据库访问；Electron 主进程负责窗口、系统对话框、文件等桌面能力、应用生命周期以及 IPC 适配。普通请求可以通过 Endpoint Registry 生成 HTTP 和 IPC 两种入口，因此不少业务逻辑是共用的。

边界仍有模糊处。流式消息需要单独处理 SSE 和 IPC，Electron 主进程也会参与服务启动、IPC 注册和部分后台服务启动。问题更多出在运行时组装和传输适配横跨两个入口，而不是核心业务逻辑完整复制了两份。后续应让两个入口都调用明确的服务运行时接口，把 IPC、HTTP、SSE 保持为薄适配层。

### 6. 为什么选 SQLite？遇到过什么问题？

Mint 最初定位是本地桌面应用，SQLite 不需要额外部署数据库服务，能和本地文件、FTS5 及 `sqlite-vec` 一起构成本地数据链路。项目的本地单用户工作负载下，这个取舍比较合适。

限制主要有两类：SQLite 同时只有一个写入者，摄入和索引重建并发时需要处理写锁；项目通过 WAL 和 `busy_timeout` 缓解读写等待，但没有消除单写者约束。Electron 打包还增加了 `better-sqlite3` 和 `sqlite-vec` 的原生 ABI、动态库路径和平台构建成本。

### 7. 如果转向多人共享、支持多用户，你会怎么设计？

我会把服务端改成共享数据的权威来源，并建立组织、知识空间、成员和权限关系。权限过滤要在检索阶段生效，引用来源也要再次校验，避免模型检索到用户无权访问的内容。

关系数据可以评估 PostgreSQL；向量规模和过滤需求合适时，可以先评估 pgvector。原始文件放对象存储，摄入、解析和 Embedding 由持久化队列中的 worker 处理，AgentRun 状态持久化并能跨实例传播事件。SQLite 可以保留为客户端缓存或离线草稿，再按实测决定是否拆分服务。

## 二、知识库与检索

### 8. 用什么 Embedding 模型？维度是多少？Chroma 和 sqlite-vec 分别做什么？

默认 Embedding 配置是 BGE-M3、1024 维，通过 OpenAI 兼容接口调用，默认地址是本机 Ollama 的接口。模型名和 URL 可以配置，但目前向量链路要求 1024 维，SQLite 的 `sqlite-vec` 表也固定为这个维度。

FTS5 负责关键词召回，选中的向量存储负责语义召回。默认使用 SQLite 内的 `sqlite-vec`；Chroma 是实验性的替换后端，不是和 sqlite-vec 同时各管一段。两种后端都由 Mint 调用 Embedding 服务生成向量。

### 9. 为什么选择 Chroma，而不是其他外部向量库？

当时目标是验证外部向量库能否通过 `VectorStore` 接口替换，而不是证明 Chroma 在性能或功能上胜过 Qdrant、Milvus 等。Chroma 的 collection API 覆盖了 Mint 当前需要的 upsert、query、get 和 delete，适合作为第一款外部适配器。

我没有做同语料、同候选数的外部向量库横向基准，不能说 Chroma 是比较后胜出的。代码把它标为实验适配器，需要单独运行 Chroma Server；连接测试也不等于完整生产检索性能已验证。

### 10. 加权 RRF 的权重怎么定？调过吗？有没有和朴素 RRF、加权求和做过对照？

当前 legacy 分数是：

`0.6 / (60 + 关键词排名) + 0.4 / (60 + 向量排名)`

一路没有命中时，该路贡献 0；分数乘以 1000 是为了保持既有分数量级。关键词权重略高，是一个偏保守的工程先验：精确术语命中相对稳定，向量召回补充语义改写。0.6/0.4 并不是离线调参后证明的最优值，`k=60` 也没有在 Mint 的数据上系统校准。

现有测试主要验证排序逻辑和兼容性。我没有在同一评测集上正式比较等权朴素 RRF、0.6/0.4 加权 RRF 和归一化加权和。RRF 避免直接相加 BM25 和余弦距离的原始分数尺度，但这不能证明当前权重优于其他权重。

### 11. Wiki 健康诊断检查什么？矛盾知识怎么处理？

`wiki_lint` 检查 frontmatter、必填字段、Schema 标签、断裂链接、未编译资料、manifest 与页面不一致、索引漂移，以及没有入链且不在索引里的孤立页面。这里的“孤立”指 Wiki 页面，不是图谱中的实体节点。它不做通用近重复或语义矛盾审计。

Claim 生命周期会处理一种有限的冲突信号：同一 `normalizedKey` 下文本相同，会强化已有 Claim；键相同但文本不同，会将新 Claim 标为 `contested` 并记录 `contradicted` 事件。这是候选冲突检测，不代表系统已经证明哪条知识错误或自动完成了裁决。当前搜索结果也没有完整暴露 Claim 的冲突状态，所以不能说回答一定会主动提示用户存在冲突。

### 12. 增量摄入时，旧 FTS 和向量怎么同步？有没有一致性问题？

页面变化时，搜索文档和 FTS 索引在 SQLite 事务中替换；之后按文档 ID、模型、维度和内容 hash 检查向量，只为变化的内容重新生成 Embedding。SQLite 查询会检查向量 hash 是否等于当前文档 hash，避免旧向量冒充新内容。向量失败时，FTS 仍可用，失败状态可以显示和重试。

FTS 和向量不是一个原子事务，所以会有短暂的向量覆盖缺口。Chroma 目前没有 SQLite 那种当前文档 hash 联查保护；写入失败时，旧向量可能仍参与检索。因此我不会把 SQLite 的旧向量过滤保证套用到 Chroma。

### 13. 如果检索到的证据本身就是错的，会不会“有来源地胡说”？

会，这是 Mint 当前仍存在的风险。引用能说明答案对应哪份检索资料，不能证明资料本身为真。摄入时验证 Claim 的证据片段是否能在原文中找到，也只证明片段确实来自原文，不证明原文内容正确。

Mint 做了来源归档和引用追溯，生命周期能标记部分过期或冲突信息；但它没有对所有来源做独立事实核查，冲突状态也没有完整进入搜索和回答决策。所以我会说系统提高了可追溯性、减少部分无依据回答，不会说“解决了幻觉”。

### 14. 检索覆盖率、引用证据匹配率和引用覆盖率分别是什么？

评测里有三个不同检查：

- **检索覆盖率**：评测用例要求的来源文件、chunk 和最低引用数量是否在检索结果里命中。
- **引用覆盖率**：答案引用是否满足对应的来源、chunk 和最低引用数量断言。
- **引用 grounding**：答案中的引用标识能否在本轮检索结果中找到。

这些指标不是“答案语义上被证据支持”的同义词。尤其“引用证据匹配率 100%”容易让人以为做了语义事实核验；更准确的名称是“引用来源身份与检索结果一致率 100%”。

## 三、Agent Runtime 与韧性

### 15. 你提到韧性治理，具体做了哪些工作？

我把治理放在 ReAct 执行的几个关口：工具调用前有参数校验、权限和风险策略；执行时有超时、有限重试和调用轮数控制；需要人工确认的操作通过审批暂停。AgentRun 记录生命周期事件并通过 SSE/IPC 推送运行状态。

如果进程重启时工具结果未知，我不会自动重放可能已发生副作用的操作，而会标记中断状态并要求用户选择恢复动作。它的目标是限制失控、保留诊断线索和提供恢复路径，不是保证所有故障都能自动续跑。

### 16. 工具调用应该重试、放弃，还是升级给用户？实际重试策略是什么？

设计原则是：网络暂时不可用、超时等可能恢复的错误，在操作可安全重复且预算还允许时可以重试；参数校验、工具不存在、权限拒绝和配置错误，重试相同输入通常没有意义；可能产生外部副作用的工具应要求审批。进程中断后结果未知时不能擅自重放，要给用户明确确认入口。

实际代码设置了 `toolMaxRetries`，默认 5、限制在 0–10；外层退避基数是 1 秒，按指数增长，封顶 16 秒。但工具执行器通常把失败转成结构化结果返回，外层 `retry()` 会把它当成 Promise 正常完成，因此当前并非所有工具失败都真正重试。常见失败会交回 ReAct，模型可以基于错误改选方案。

### 17. “调用预算”按什么计？超预算怎么办？

当前可见的 ReAct 工具预算主要按调用次数计，运行策略接口支持总调用数、单工具数和单轮单工具数。ReAct 默认最多 5 轮，设置上限 20 轮。这些工具次数策略是可选参数，评测会显式传入；正常聊天路径目前没有统一的生产总工具次数预算。

Token 会记录，长上下文也会压缩，但没有每次运行的 Token 或金额硬上限。预算实际生效时，超限工具会被拦截，并要求 Agent 基于已有结果作最终回答。工具预算与 Token/金额预算是不同概念。

### 18. 工具权限怎么落地？举一个被策略拦截的例子。

工具执行前先检查工具是否注册且启用，再校验输入 schema 和工具自身权限；随后按工具元数据、参数和资源路径执行策略。HTTP 工具拒绝 localhost、私有网段等目标；Bash 检查工作目录和路径范围；高风险命令或外部副作用操作会要求审批。

一个具体拦截例子是：模型调用 `http_fetch` 请求 `http://127.0.0.1/...`，策略识别出这是本机回环地址并拒绝，不进入实际工具执行。对公网地址发 POST 则会请求用户审批。实现见 [tool-policy.ts](/Users/wangding/WorkSpace/personal/ai-chat/server/application/agent-runtime/tooling/tool-policy.ts)。

### 19. AgentRun 事件模型是什么？SSE 断线、乱序和丢事件怎么处理？

运行事件有 `runId`、可选 `conversationId`、递增 `sequence`、事件类型和载荷，包括轮次、工具开始/结束、审批、答案和运行终态。单个 AgentRun 会按顺序发布；前端会忽略重复或不递增的序号。

但持久化只保存一部分生命周期事件，不保存完整答案/思考内容、工具参数和所有 SSE chunk。SSE JSON 中带 sequence，却没有原生 `id:` 和 `Last-Event-ID` 回放；客户端不缓存乱序事件，也不检测序号跳跃后补拉。审批恢复时能继续仍在内存中的同一运行并接收后续事件，但不补发断线期间事件。进程重启恢复主要是诊断与恢复动作，不是完整事件回放。

### 20. 为什么选 SSE，不选 WebSocket？用户中途取消怎么处理？

Agent 的主要流量是服务端向客户端推送状态和回答；发消息、审批、取消可以通过普通 HTTP 或 IPC 发送。因此 SSE 加控制请求已经符合主要通信模式，不需要为了运行状态流维护一条 WebSocket 双向连接。Mint Web 路径使用 `POST + fetch` 消费 SSE。

当前取消链路还不完整：Web 客户端中止 fetch 不等同于服务端 Agent 已收到取消；HTTP 路由主要结束响应，没有将断开统一传播为 Agent 的 `AbortSignal`；Electron abort 也只是清理事件监听。完整设计应按 `runId` 提供幂等取消，把 Signal 传给模型请求和工具，并让 AgentRun 只发布一个终态 `run_cancelled`。网络断开和用户主动取消也应分开处理。

## 四、Jev 与语义决策

### 21. Jev 是什么？为什么不用通用 LLM 输出 JSON 或传统分类器？

Jev 是 TypeSafe 的 System One 判定接口，调用方传入 state 和类型化问题，问题可以是 `choice`、`score` 或 `noul`。Mint 用它做动态 Agent 候选选择、记忆门控，以及对检索候选的语义相关性判断。

通用 LLM 输出 JSON 当然也能完成类似任务。Jev 的取舍是让调用方声明选项和判断类型，减少自定义 JSON 协议和解析；它并不保证语义判断更准确。类别固定、有充分标注数据的任务，传统分类器也可能更合适。

### 22. Agent 路由阈值怎么定？阈值错了会怎样？校准过吗？

默认最低路由置信度是 0.5，设置可以调整到 0–1。低于阈值时，Jev 结果会被拒绝并继续走 legacy 路由；太高会增加回退，太低则会接受不确定的路由并可能选错专用 Agent。

这个阈值是工程启发值，没有用独立人工标注集做路由置信度校准。Jev 的 confidence 也不能直接当成已校准概率。项目里 Judge 的校准能力和 Agent 路由的校准是两件事，前者不能替代后者。

### 23. 记忆门控误判的代价是什么？漏记和错记更担心哪种？

默认记忆价值阈值是 0.4，设计时偏向减少用户长期偏好、目标和纠正信息的漏记。漏掉这些信息会降低后续个性化效果；错记则可能把错误或过时信息带入之后的回答，敏感信息被不必要地记住代价更高。

当前 `skip` 是 Jev 的终局结论，不会再回到 legacy 启发式；只有 Jev 不可用时才回退。因此阈值如果造成系统性漏记，旧逻辑不会补回。后续应按记忆类别区分漏记和错记成本，并提供纠正和删除能力。

### 24. Jev 重排和 Cross-Encoder 比，效果和成本如何？

Mint 的 Jev rerank 是默认关闭的实验能力：按 legacy RRF 取前 8 个候选，再逐个判断候选能否直接回答查询；失败时回退 legacy。项目没有部署 Cross-Encoder，也没有同一候选集上的质量和成本对照。

概念上，Jev 依赖外部服务，需考虑网络延迟和调用费用；Cross-Encoder 需要部署模型，成本更多来自算力和运维。实际选择应在同一数据集和候选数下比较 nDCG/MRR、Recall@k、回答质量、P95 延迟及单次查询成本。

## 五、RAG Eval 与指标

### 25. 评测集多大？谁出的？有没有无答案或对抗样本？

当前 `wiki-rag.json` 是 25 道题，基于 10 篇固定原始资料；每题跑 3 次，共 75 次运行。题目和 `requiredSourceFiles`、`mustContain`、`mustAbstain` 等预期断言由我作为项目开发者手工编写和维护，没有独立双人标注或仲裁。README 仍显示 20 题，已经落后于当前 JSON。

当前有 3 道拒答题和 1 道专门的安全对抗题。对抗题数量和覆盖范围有限，而且它的断言不够严谨，不能据此宣称安全能力已经充分验证。

### 26. Pass@3 和 Pass^3 怎么定义？

每题跑 3 次，Pass@3 是至少一次通过的题目比例；Pass^3 是 3 次全部通过的题目比例。评测器还支持根据重复运行结果按组合公式计算；当每题正好跑 3 次时，这两个指标就分别等价于“至少一过”和“三次全过”的题目比例。

这里的 `passed` 是复合门槛，包含答案断言、检索和引用、拒答、工具策略与预算等，不是纯语言质量评分。

### 27. Pass@3 和 Pass^3 差 8 个百分点说明什么？分析过失败分布吗？

如果 96%/88% 来自同一份 25 题、每题 3 次的报告，题级上相当于 24 题至少过一次、22 题三次全过：2 题间歇失败、1 题三次都失败。但这不能单凭差值断定是模型随机性，还要看这些题的逐次检索、引用和工具轨迹。

仓库保存的报告里没有 96%/88% 这组配对数值。相近的 9 月 22 日报告是 96%/84%，9 月 29 日最新报告是 96%/80%。最新报告里有 4 道间歇失败题、1 道三次全失败题；间歇失败主要是检索覆盖检查通过但答案未生成引用，持续失败的是 `security-001` 工具断言。不能把这份分布冒充成 96%/88% 那一轮的失败分布。

### 28. RAG Eval 是自动还是人工？Judge 偏差怎么控制？

主通过率来自确定性检查；LLM Judge 或 Jev Judge 是可选辅助，只评通过确定性硬门槛且定义了 rubric 的结果。Judge 按维度评估答案和证据，结果单独记录，不会悄悄改写确定性 Pass 指标。

项目实现了人工校准模板和一致率计算，但当前仓库没有对应的人类标签和校准结果，所以我不声称现有 Judge 已完成校准。Judge 输入包含确定性结果，可能产生锚定偏差。

### 29. 有没有看起来漂亮、但实际意义有限的指标？

最容易被过度解读的是“检索覆盖率 100%”。它检查评测用例要求的来源或 chunk 是否命中，不等于召回完整、排序合理或证据语义上支持回答。

我会把它称为“必需来源检查覆盖率”，并与 Recall@k、引用支撑情况和逐题失败分布一起报告。

### 30. 如果面试官质疑 100% 指标是刷出来的，你怎么自证？

我会提供具体报告版本、数据集、固定语料、运行配置、逐次结果和计算代码，让面试官随机抽题复算；也可以用原始资料在干净的隔离 Wiki 上重跑，并保留所有失败。

同时要说明 100% 的精确定义：引用 grounding 检查的是答案引用标识是否能在本轮检索结果中找到，不证明证据语义上支持主张，也不证明原始资料真实。它是特定小型评测集上的历史结果，不是生产环境 100% 正确率保证；不同报告版本的指标也会变化。

## 六、SDD、规模与复盘

### 31. SDD 闭环最痛的一环是什么？举一个真实 Bug。

最痛的是验证能否覆盖用户真实的状态时序，而不只是让单测或 mock 通过。首次连接模型后发送第一条消息，如果运行失败，失败状态应该显示在刚创建的会话中，用户能继续重试或修复。

实际实现里，失败状态 setter 仍绑定空会话 ID；会话创建后，失败消息写错目标，用户看不到失败状态。修复是让 setter 显式接收目标会话 ID，并通过浏览器失败场景和类型检查验证。验证时还发现两条同 URL 的 SSE mock route 后注册者覆盖先注册者，导致失败分支没真正被测试；随后调整 mock，让失败分支真正执行。

### 32. 这个项目最让你担心的问题是什么？现在解决了吗？

最担心的是答案“有来源，但来源本身错、过期或互相矛盾”。来源引用和原文片段检查提升了可追溯性，但不代表来源为真；冲突状态也没有完整传到搜索和回答决策。

所以没有完全解决。我会说 Mint 能让用户更容易核验来源、减少一部分无依据回答，不会说它彻底解决了幻觉。

### 33. 如果给你 10 倍数据量，哪个模块先遇到瓶颈？你怎么改？

如果 10 倍指 Wiki 页面和切片数，我最先担心每次摄入后扫描整个 Wiki 并重建索引。单次摄入的工作量会随着全库增长，还会增加 SQLite 写入压力。

我会让摄入明确产出新增、变更和删除页面清单，只更新对应的 FTS 文档；向量生成改成持久化、可恢复的批处理任务，按内容 hash 跳过未变化项。然后用真实 10 倍语料压测摄入耗时、写锁等待、向量回填速度和查询 P95，再决定是否拆分存储。

### 34. 哪些是“够用就行”的妥协？哪些必须坚持？

单机 SQLite、先保留 FTS、向量异步补齐，以及暂时不做分布式，都是可以随实测演进的妥协。短时间向量索引不完整可以接受，但状态要可见、能重试，并能退回 FTS。

不能接受静默使用过期向量、来源断链、失败不留记录或重试造成重复副作用。可以先不追求最高吞吐，不能牺牲数据身份和失败透明度。

### 35. 如果现在从头重做，哪三个设计会改？为什么？

第一，从第一版就把摄入和索引设计为增量、持久化、可恢复的流水线，避免每次扫描全库。第二，一开始就定义完整 AgentRun 取消与断点恢复协议，包括按 `runId` 取消、事件回放和终态保护。第三，尽早建立有版本、来源和人工复核记录的评测集，纳入错误、过期、矛盾、无答案和对抗样本，并把 Judge 人工校准作为独立验收。

这三项分别针对规模增长、运行中断和评测可信度；它们会影响系统的基础边界，越晚补越容易付出迁移成本。
