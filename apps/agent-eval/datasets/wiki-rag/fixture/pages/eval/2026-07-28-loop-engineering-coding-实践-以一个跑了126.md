**0. 赞美伟大的openAI**

- 什么叫两周n次重置还送一张重置卡？
- 老佛爷付过了。
- 和Anthropic真不熟，骗你的，是它和我不熟。

**1. 这套实践是怎么来的**

最近我们正好要重构一个跨仓产品。开工不久就发现，真正拖慢交付的不是某个 issue 的代码难写，而是需求、代码、验证和知识分散在不同地方。

- 产品讨论在群聊里，设计判断却留在一次次对话中。
- 代码分散在多个仓库，测试、截图和线上结果也各有去处。代码合并后，仍很难证明真实链路已经跑通。
- 新会话总要重新解释需求。Agent 能做完其中一步，下一位接手的人仍要自己拼回上下文。
所以这次重构没有只改代码，也顺手重做了交付流程。我们先用 Issue 保存目标和恢复入口，再逐步接入需求对齐、隔离开发、自动化回归、失败留证、真实消息端 E2E 和人工验收。做到 P1b-8 时，主 Issue、跨仓边界、PRD、1:1 原型、最终 Spec、验证矩阵和实施 Plan 已经连成一条完整的 Coding Workflow。且**这次开发使用 GPT-5.6 Sol（Ultra + Fast），仅仅在 E2E 开发Loop阶段就****连续运行 126.7 小时，消耗约 5.56B tokens****。**

回头看，这不是一条包办一切的大 Loop。完整交付是一条从需求到上线的 Workflow，里面有实现验收、发布回归等多个 Loop。交付留下的决定、失败、证据和方法，还会进入另一条跨项目运行的知识改进 Loop，供后续任务取用和修正。另外，Loop只是一个概念，别管Loop不Loop，顺手、有效最重要。

**2. 一条 Coding Workflow，多个 Loop**

整套实践的外形是一条从需求到上线的 Coding Workflow。里面既有反复执行直到满足停止条件的 Loop，也有一次性的质量门和必须由人拍板的决策点。

这里的 Workflow 指完整流程，不特指固定编排或预先写死的 DAG。

- 定义与探索：先恢复已有上下文，再用 Grill Me、PRD 和 1:1 原型把模糊需求变成可以据此验收的约定。简单 Issue 可以按 Workflow 的规则跳过不必要的步骤。
- 任务闭合（Spec-to-E2E Loop）：从已确认的 Spec 出发，反复实现、测试、另起上下文复核、真实 E2E 和取证，直到人工验收通过，或者遇到必须交回人的分叉。
- 可选观察 Loop：长任务开始后，可以让 Heartbeat 周期性唤醒一个独立观察线程。它只报告进度和异常。只有命中预先确认的条件时，才向 Coding 线程发送 checkpoint 请求。它不改代码，也不负责验收。
- 发布验证 Loop：人工验收通过后检查 MR。合并后再完成构建、升级、线上版本确认、真实入口冒烟测试、回归，以及必要的回滚和回滚后复测。
- 知识改进 Loop：定期读取多次 Coding Loop 的运行样本，找出重复纠正、无效轮询、过大的回归集，以及高耗时却没有产生更强证据的步骤。修改下一次 Loop 后，再由后续运行验证它是否真的更顺。
本文标题中“运行了 126.7 小时的 Loop”，指的就是 Spec-to-E2E Loop 本身，不包含此前的需求澄清和此后的发布、知识沉淀。

Issue 是整条流程的共同入口，保存目标、负责人、状态、影响仓库、阻塞项、分支、MR、验收结果和产物链接。PRD、Spec、原型、测试和验收材料跟着 Repo 版本化。API、数据库、运行状态和用户实际看到的结果，用来证明系统此刻是否成立。Issue 负责把这些材料串起来，不负责复制一份大而全的正文。

**3. 一个复杂 Issue 怎样沿 Workflow 走到上线**

**3.1 Issue 起点：从归因任务工作台到人机协作任务中枢**

P1b-8 最初只是一个归因任务工作台：归因结果在群聊里发送和消费，用户希望在 Web 端管理它的状态、负责人和结论。顺着真实使用方式往下想，一个只服务归因任务的后台很快就显得太窄。任务从 Bot 进入，还要在 Bot 和 Web 两端被筛选、分配、推进和验收，执行者既可能是人，也可能是 Agent，后续的任务还有可能是运行较长的评测任务，需要快速@bot查看具体状态。既然我们已经在不同群里积累了一定的上下文，而且web和bot端天然就架在那（而不是为了醋而包饺子），我们干脆直接跟风把它扩成了一个 Bot + Web 的人机协作任务中枢。

这样，Agent 接到的就不再是一张空白任务卡。Issue 会同时带上项目背景、领域知识、可用工具和验收方法。群聊负责自然语言输入和即时协作，Web 负责看板、详情、筛选、执行记录和证据浏览，两端始终操作同一条 Issue。

**3.2 开工前：先恢复上下文**

新会话开始时，我们不会立刻让 Agent 写代码，也不会把整个 Wiki 一次塞进 Prompt。通常先按由近到远、由事实到原因的顺序，整理一页“本轮开工摘要”（Context Snapshot）：

1. 先看当前 Repo：读取 AGENTS、代码、测试、架构文档，以及本轮 PRD、Spec、Plan 和验收材料，确认系统现在是什么样。
2. 再看当前项目：读取项目索引、当前 Issue、项目 Workflow 和项目知识，确认哪些决定已经做过。
3. 然后看历史交付：查看相关的消息、旧 Issue、MR、Commit、验收和发布记录，区分真实跑过的路径与只写在文档里的方案。
4. 再补共享经验：从全局 Wiki 查询跨项目工程经验、共享流程和共享 Workflow。
5. 最后才回原始讨论：只有现有产物解释不了某项取舍时，才回看对应 session 或原始群聊。Coding 对话自动上传、挂接 Issue 和回放已有对应 hook 方案；这里不展开实现，只把它视为恢复上下文的一条来源。
这页开工摘要只保留会影响本轮执行的内容：沿用哪些约束，来源在哪里，哪些信息可能过期，哪些决定已经被替代，还有什么需要现场确认。它既是开工输入，也是任务中断后的恢复点。

**3.3 主 Issue、主仓与跨仓协作**

需求进入系统后，先确定由哪个项目负责，再判断会修改哪些仓库。负责项目由业务含义、负责人和最终验收归属决定。主仓则要看核心数据由谁持有、主要接口在哪里，以及最终从哪里完成验收。

P1b-8 的主仓不是预先指定的，而是调查后定下来的。任务、运行记录、Agent 工具和消息运行时的关键事实都在主后端仓库，最终联动验收也要从这里发起，所以它成为主仓。前后端仓库负责独立的页面、权限和代理接口，各自有实现、测试、MR 和 Web E2E，因此分别建立子 Issue。

整个过程按下面的顺序走：

1. 先在负责项目里建立主 Issue，记录原始诉求、目标、明确不做的内容、初步验收和未决问题。此时可以暂不决定具体改哪些仓库。
2. 调查数据由谁持有、调用方向是什么、最终从哪里验收，再确定 Main Repo。
3. 其他仓库只有在形成独立设计、独立 MR、独立验收或独立 Owner 时，才建立 Child Issue。
4. 主 Issue 记录受影响的仓库、各仓分支和 worktree、MR、负责人及最终验收入口。
5. 跨仓只维护一份最终 Spec。子 Issue 只说明本仓怎样实现、怎样接入和怎样验收，不复制另一套完整产品语义。
这套分工只想解决一件事：产品语义定义一次，每个仓库保留自己的版本历史和交付责任。主 Issue 能看到全局进度，但不会吞掉各仓真正需要随代码版本化的文档与证据。

**3.4 Grill Me：把模糊需求压成决策**

主 Issue 建好后，我们先做需求对齐，不急着生成 Plan。

其中一个看起来很小的问题是“群里被 @ 的人能不能直接设成负责人”。继续问下去才发现，它同时涉及成员是否存在、谁有权限添加成员、加成员和分配任务能否原子完成，以及失败时群里应该看到什么。一句顺手的产品要求，已经横跨产品、权限、数据和通知。

这里用到 Grill Me。Agent 先调查代码和现有事实，再沿目标、边界、例外、取舍和验收追问。任务属于群还是工作区？人和 Agent 能否共同负责？Agent 执行成功是否等于业务完成？谁能验收？Web 创建的任务没有来源群时，结果发到哪里？这些问题如果留到实现阶段，页面、API、权限和运行时很容易各自长出不同语义。Agent 负责查事实，人负责做会改变产品方向的决定，最后才形成一组可执行的约定。

原始 Grill Me 的问题是太细。Agent 可能连续问几十个甚至上百个问题，把代码里能查到的事实、低风险默认值和需要人拍板的产品分叉混在一起。

我们改造了一下，它会先确认本轮决定写回哪里，再把未决点分成四类：

- 可查明事实：先调查代码、文档和运行状态，查不到或确实取决于人的意图时才提问。
- 决策分叉：会改变目标、范围、行为、不可逆影响或验收标准的问题，一次只问一个。
- 澄清细节：互不依赖、影响较低的同类问题，合并成 2–3 个小问题一起确认。
- 安全默认项：符合惯例、可逆且影响较小的选择，先形成默认决策包，再集中确认例外。
一个主题结束后，再做一次全局一致性检查，只重新打开彼此冲突的决定。不同领域继续使用自己的事实源：Coding 写回 Issue 与 Spec，写作写回文章 Wiki，不额外制造平行记录。

我们用过去 7 天的 Grill Me 对话和最终选择进行重放后，问题数量和打断明显减少，但关键分叉仍然保留了。

**3.5 持续Grill Me：PRD、1:1 原型与 Browser Automation**

这里的 PRD 仍由 PM 对产品决定负责，Agent 不替 PM 设计产品。PM 负责用户问题、价值、范围和业务规则；设计负责信息架构、交互和视觉状态；RD 负责技术约束、数据与 API、可行性和故障恢复；QA 把验收意图、边界和失败路径变成 E2E 矩阵。四类责任不一定对应四个人，但每个决定都要有明确的 owner，且不再是“人-人-bot”的形式，而是加上了状态流转之后的“人-bot-人”的形式。但是由于我们还没有设计明确的状态流转流程以及这是产品，所以这个整个过程就我自己做了.jpg。形成共识后，结论与源链接也要写回 Repo，而不是只留在会议或聊天里。

PRD 负责写清用户、场景、任务模型、状态、角色权限、通知和验收。只靠文字仍然不够，复杂页面和状态流很容易让Agent在产品、rd各自脑补，所以我们继续把产品合同拆成三份互相约束的产物：

1. Web 设计契约：入口、筛选、六状态看板、卡片字段、新建弹窗、任务详情、状态确认、Run 详情、人员与通知边界。
2. 可交互 1:1 HTML：可以真实点击、切换状态和走完关键交互，不是一张静态示意图。
3. 视觉合同与截图集：固定视口、主题、语言和代表状态，让实现与验收引用同一版页面事实。
P1b-8 的原型覆盖 21 个页面状态，包括看板、筛选、新建、负责人和验收人选择、六种任务详情、状态菜单、状态确认、Run 详情、空态与 Gallery。每个状态再覆盖浅色和深色、中文和英文，最终得到 84 张 1600 × 1000 截图。清单和 Hash 用来锁定大家正在讨论的具体版本。

**Browser Automation** Skill 也在这一步进入。我们的 Skill 不会见到网页就直接操作 DOM，而是按稳定性选择入口。跨端页面、视觉定位和用例维护也已有对应工具方案；本次没有因为“工具更多”就额外引入，只有页面本身是验收对象时才走真实 UI：

- L0：已经有对应 Skill，直接使用。
- L1：有官方 API 或 CLI，优先调用。
- L2：有认证方式相同的相邻 Skill，复制并改造。
- L3：全新网站先用浏览器捕获真实请求，再沉淀为 Skill 或 CLI。
- L4：一次性任务可以复用登录态直接调用 HTTP。
- L5：没有稳定接口，或者页面本身就是验收对象时，才走真实页面、截图和 Trace。
我们常说的“浏览器造 CLI”主要发生在 L3。浏览器先发现网站真正调用的接口，Skill 或 CLI 再把这次发现变成可复用能力。到了 1:1 原型和 Web E2E，页面本身就是验收对象，Browser Automation 才直接遍历页面状态、批量截图、保存 Trace 和回读结果。

这样，原型就不会停在“大家曾经看过一次”。页面状态可以直接变成验证 case，截图成为视觉证据，浏览器 Trace 证明交互路径真的发生过。后面的 Spec、实现和 E2E 都引用同一版产品事实。

P1b-8 的 1:1 原型：六状态任务看板。它是产品与视觉合同，不是已上线实现。

Agent Run 详情：执行过程与证据单独展示，Run 成功后仍由人完成任务验收。

原型 Gallery：21 个页面状态 × 2 个主题 × 2 种语言，共 84 张固定视口截图。

**3.6 依旧Grill Me：从 Canonical Spec 到验证矩阵和 Plan**

前面的 Grill Me 解决的是“产品到底要做成什么”。PRD 和 1:1 原型把这些决定变成了可阅读、可操作的产品约定。接下来进入工程设计，问题也随之变化：这些约定能不能被现有代码实现，又该怎样验证。因此，在生成 Plan 之前，我们会再做一轮 Grill Me。

**Canonical Spec**

这一轮按三步走：

1. 先查事实。Agent 对照 PRD、原型、已经确认的决定和现有代码，找出材料之间的冲突，以及实现和验收边界里缺少依据的地方。能从代码和已有文档查清的，自己补齐。
2. 再处理真正的分叉。只有会改变产品行为、技术路线或验收方式的问题，才交给人决定。如果方案引入了新的组件、中间件或外部服务，而仓库里缺少本次实际采用的版本和内部约束，就请负责人补充对应的技术文档。
3. 最后收敛成 Spec。Agent 把原始链接和适用范围写进 Issue 的来源清单，把 API、配置、容量、兼容性、故障和回滚边界写进 Canonical Spec。产品行为、技术边界、失败路径和明确不做的内容全部闭合后，材料才形成 Canonical Spec；还有缺失、冲突或未决项，就继续调查和 Grill Me，不进入验证矩阵和 Plan。
这份 Spec 同时约束产品行为和系统实现。数据模型、状态变化、权限、API、Bot 与 Web 行为、Agent Run、通知、幂等、多实例、失败恢复和明确不做的内容，都要与已确认的 PRD 和原型一致。跨仓仍只有一份最终 Spec。其他仓库的文档只补充本仓如何实现和验收，并链接回主文档。

材料变多以后，Agent 首先需要一个稳定入口。我们在 docs/issues/<issue-slug>/README.md 维护当前清单。README.md 只负责指向仍然有效的来源、决定、PRD、原型、最终 Spec、验证矩阵和 Plan。正文分别留在对应文件中，每次运行的证据进入 acceptance/<run-id>/。阶段推进时更新链接、版本和状态，被替代的文件明确标记失效。

例如“Agent 执行成功不等于任务完成”这条决定，会在 Spec 里变成两套独立状态，在验证矩阵里变成“Run 成功后 Issue 仍等待人工验收”的 case，最后才在 Plan 里拆成数据模型、接口、页面和测试任务。这样，产品决定不会靠口头共识穿过几个阶段。

到这里，Spec 已经回答了系统应该做什么，但还没有回答怎样证明这些行为真的成立。如果直接生成 Plan，Agent 很容易把任务拆成一串实现步骤，验收只能等做完以后再补。于是，我们先把 Spec 中的产品行为、技术边界和失败路径逐条变成 E2E Matrix。

**定义怎样证明完成**

这里所谓的“验证合同”，就是 E2E Matrix。它在实现前写好，把每一条产品行为和系统约束翻译成可以观察、可以判定的 case。

P1b-8 有 88 个编号 case，其中 14 条 P0 决定第一轮先跑什么，其余 74 条为 P1。最终仍要达到 88/88。覆盖范围包括：

- Bot 创建、查询、编辑、分配、身份解析和权限。
- Web 看板、筛选、新建、详情、状态确认、主题与多语言。
- Bot 创建、Web 修改、Bot 再读取的同一 Issue 联动。
- Agent Run 启动、提交、失败、改派、迟到结果和人工退回。
- Workspace 隔离、多 Bot 身份、多实例并发与崩溃恢复。
- 普通群聊、私聊、subagent、reflow、lookback、media、scheduled 等旧能力回归。
其中一些 case 专门测试正常页面看不出来的问题，例如跨 Workspace 数据泄漏、任务改派后旧 Agent 的迟到结果、多实例同时启动同一个 Run。它们决定了这套系统能不能被真实团队使用。

每个 case 同时规定用户应该看到什么，以及接口、数据库和运行状态中要核对哪些事实。涉及 Web 就保存截图和 Trace，涉及 Bot 就保存收发消息 ID，涉及 Run 就保存 Run 记录、Task、尝试次数和证据。

有了验证合同，长程 E2E 才有可判定的目标。Agent 每改一段代码，都知道下一步检查什么。失败时知道保存哪份现场证据，修复后也知道要复测哪一个原 case。

**Spec 与验证矩阵稳定后，再生成 Plan**

PRD、原型、Spec 和验证矩阵稳定后，我们才重新生成跨仓实施 Plan。当前 Plan 有 12 个任务，每个任务写清依赖、要修改的文件、先失败再通过的测试命令、回归范围、复核节点和负责的 E2E case。上游约定变化后，Plan 也要重新推导。Plan 很长，复核量并不小，但这个大 Issue 建立在前面多个小 Issue 的经验之上，仓库里已经积累了写 Plan 的项目规则，因此复核不需要从零开始。

**Superpowers：去芜存菁**

Superpowers 是一组覆盖 brainstorming、Spec、Plan、TDD、worktree、subagent、fresh review、完成前验证和分支收口的软件开发 Skills。它给我们的启发主要是几条工程纪律：

- 设计没有被接受就不进入实现。
- Plan 要能被另一个上下文接手。
- 实现与审查尽量隔离。
- 完成结论需要新鲜证据。
它的缺点也很明显。整套 Skills 全量启用后，小任务也会经历多次切换、落盘、确认、subagent 分发和 review。极细的 Plan 与逐任务 reviewer 会消耗大量 Token 和上下文。社区里已经有人讨论单体详细 Plan 的效率和Codex 5.4 多轮 review 放大的执行成本。近期 r/codex 也有 GPT-5.6 Sol 用户认为全量启用后运行时间和额度消耗增加（讨论）。不过这些都是使用体验，没有受控 benchmark。

更直接的论据来自 OpenAI 的 GPT-5.6 Model Guidance。官方建议减少重复指令与示例、简化工具描述。在一组内部 coding-agent eval 中，更轻的 system prompt 得分约提高 10–15%，同时减少了 41–66% 的 Token 和 33–67% 的成本。这些数据只是方向性结果，仍需在自己的代表性任务上验证。官方同时强调，**GPT-5.6 已经能从上下文推断更多用户意图，不必再把每一步都规定死，但领域上下文、硬约束、审批边界、成功标准和必要证据仍然要明确。**

这不能证明 Superpowers 在 GPT-5.6 Sol 上必然构成“反向优化”，但它为我们的改造方向提供了更直接的依据：不再无差别叠加全部流程，而是按任务复杂度路由。减少模型已经能够承担的重复编排，保留事实源、质量门、人工决策点和验收责任。

我们没有逐个修改 Superpowers Skill，而是直接把这些原则简单朴素地内化进自己的 development workflow，别担心太简单Agent不懂，Agent太懂了：

**阶段识别：**

边界不清时停在 Define。

Accepted Spec / Plan 才进入 Execute。

真实 E2E 通过后进入 MR。

合并后才进入 Release 与 Closeout。

**Plan 按需：**

跨模块、长时间、严格顺序或需要交接时写详细 Plan。

边界清楚的小任务只保留短 checklist或/plan。

复杂度路由：简单任务由主 Agent 直接做。只有边界独立、并行收益明确时才委派 subagent或者启新thread(以直接利用不同资源.jpg)。

Review 按风险：复杂或高风险边界使用 fresh-context reviewer。简单任务先由主 Agent 自查。

验证统一：自动化测试、真实 E2E、DB / API 事实证据、配置恢复、多实例、失败复测和 Evidence 不会因为任务小就消失。

**3.7 Spec-to-E2E Loop：从执行选择到验收证据**

**开跑前的两个选择**

**执行载体**

Agent 会根据任务范围、所需工具和运行时间给出推荐，人可以直接接受，也可以改选：

- 当前线程直接执行：默认推荐。需求已经闭合、工具都在当前环境中时，不额外制造交接。
- Subagent：适合边界清楚、可以并行收口的实现、测试或复核子任务。它仍由主线程协调，不把子任务包装成一支长期协作的 Agent Team。
- 独立线程：当任务需要换一种 Agent 或模型、调用只在特定环境中可用的特定环境资源，或者需要长时间异步运行时再选。线程之间通过同一份 Spec、Issue 和证据交接，而不是依赖隐式共享状态。
这里保留“独立线程”这个选项，主要是为了调用不同 Agent，并利用不同运行环境和资源，不是为了做一个中心 Agent 持续调度的 Agent Team。

**独立的观察线程**

之所以称为观察 Loop，是因为在该县城中每次 Heartbeat 唤醒后都会重复同一轮动作：读取 Coding 任务状态，判断是否正常推进、需要 checkpoint 或已经命中安全停机条件。正常时等待下一次唤醒，发现问题时才通知或请求主线程收束。目标任务完成、失败、取消、交接或进入等待后，这条 Loop 停止。

1. 观察方式可选：不启用、只观察、异常时请求 checkpoint、到时请求 checkpoint；只有另行明确授权后，命中卡死或资源越界条件时才执行 hard interrupt。
2. 观察内容：默认看进度、停滞、工具故障、Git、测试和证据。长任务还可以加看目标进程的内存，以及目标磁盘的剩余空间和产物增长。
3. 什么时候介入：正常时只报告。命中启动前确认的停滞、资源阈值或时间条件时，先向 Coding 线程请求 checkpoint。只有已经明确授予 hard interrupt 权限，且线程卡死、无法自行落盘时，观察线程才按预先授权的条件强制停止。
4. 停下时留下什么：已经完成的事项与证据、Git 和 worktree 状态、仍在运行的进程、临时配置、未完成项、风险和恢复入口。
P1b-8 的实际 Heartbeat 观察任务：定时唤醒后读取目标 Codex 任务，并进行check

Codex 运行时支持跨 thread 通信。人确认后，可以创建一个绑定 Coding 线程的 Observer，并用 Heartbeat 周期性唤醒。Heartbeat 只负责唤醒，真正的读取、判断和消息注入由 Observer 完成，不把监控过程塞进主线程上下文。

这个线程对我们本次任务非常重要，它发现了Chrome devtools MCP不稳定，并告诉coding线程去切换成chrome的拓展。同时，他在长程任务中大大提升了我对任务的掌控感，让我没有忍不住手动接管任务。当然本次coding任务，也反哺了关于这个监控线程应该监控些什么的经验。

**Loop！**

主任务开跑时，需要把四类信息在Loop中补充：

- 本轮依据：当前有效的 Spec、验证矩阵、Plan、分支、配置和数据库。
- 范围边界：必须成立的用户行为、明确不做的内容，以及需要保护的旧能力。
- 通过条件：每个 case 要留下什么证据，谁来复核，最终由谁验收。
- 交回条件：哪些需求、架构、权限、生产或资源问题必须暂停并交回人。
我们的**Spec-to-E2E Loop skill**中，已经说明了通用的信息，跑的时候按需补充。

之前我们的习惯是，/loop xh /goal 直到E2E验证通过+其他补充信息。不过目前感觉，/goal的用处在codex里感觉不大了。搞个/loop兜底下突发的网络情况就行了。

开跑以后，Agent 先按照 Plan 推进实现任务。每完成一项，或一组边界相同的改动，就运行与它对应的最小自动化测试。代码通过后，再从 E2E 验证矩阵中选择受影响的 case，进入独立复核和真实环境验证。这里有两层推进关系：

实现任务 → 最小自动化测试 → 选择受影响的 E2E case → 独立复核 → 真实环境验证 → 保存证据

自动化测试没有通过，就继续处理当前实现任务。测试通过后，复核者根据 Spec、代码差异和测试结果寻找反例，再运行受影响的真实 E2E case。复核或真实环境一旦发现问题，先保存当时的页面、消息、接口、数据库和运行状态，然后回到对应的实现任务修复，并重跑相关测试与 case，不能改测一个更容易成功的样例。只有改动碰到公共边界时，才扩大回归范围。用户是否看见结果、API 是否返回正确内容、数据是否真正写入、临时配置是否恢复、双实例是否只执行一次，都需要分别核对。

当前这条链路已经能用 Browser Automation、Chrome DevTools、Playwright、截图和 Trace 完成页面操作与取证。跨端页面、视觉定位和用例维护也有对应工具方案；只有现有工具出现明确瓶颈时，我们才会重新评估引入。

每个通过的 case 最后都进入验收证据包。里面记录分支与提交、测试命令、消息 ID、接口和数据库摘要、截图、失败与复测、配置恢复，以及还没有覆盖的内容。这个证据包是下一节人工验收的输入。

P1b-8 把这套方式拉到了更长的尺度。它的 E2E 任务连续运行了 126.7 小时，88 个矩阵 case 已全部完成并经过复核，长程 Loop 减少的是人盯执行的时间，不是验收标准。当然，我们的监控线程发现了其中不少问题，很多流程边跑边优化，比如最小回归集、内存和磁盘监控、浏览器工具稳定性等。

**3.8 验收：看证据，不听总结**

长程执行结束后，人打开的不应该是一段“已经完成”的 Agent 总结，而是一份可以逐项核对的验收说明。我们的验证文档通常包含下面这些材料：

- 实际分支、提交、代码差异，以及它们对应的 Spec 和 Plan。
- 自动化测试的完整命令、结果和覆盖范围。
- 独立复核发现了什么，以及每个问题如何处理。
- 验证矩阵通过了多少，哪些 case 失败过、怎样修复和复测，还有哪些没有测。
- 浏览器截图与 Trace，以及消息 ID 和回读结果。
- Issue、Activity、Run、Task 等关键数据库记录。
- 临时配置修改前、运行中和恢复后的状态，以及进程和数据库两侧的确认。
- 旧能力回归、残余风险，以及是否建议进入 MR。
**P1b-8 是目前更完整的长程样本。它的 ****E2E 任务连续运行了 126.7 小时****，验证矩阵中的 88 个 case 已经完成 88/88，每个 case 都留下证据并经过复核。**

这次取证同时覆盖 Bot 端和 Web 端。Bot 端在群聊里创建、查询和流转 Issue，Web 端读取同一份任务事实，在六状态看板和详情页中展示。两侧不是两套演示数据。消息 ID、接口与数据库回读、测试结果和独立复核一起证明，它们指向同一个 Issue。下面保留脱敏后的真实验收材料。报告、消息端与 Web 端证据仍来自同一次运行，只替换名称、账号和具体业务文本。

**3.9 发布验证 Loop：MR、上线、回滚与线上回归**

这里以单仓库上线为例子哈，多仓啥的也是一样的，你的agent会安排好这个计划，我们项目里的上线loop只是给agent一个参考对象，实际的loop和写代码时一样，会出个具体的release spec，依旧loop、依旧E2E回归。

已经有一条真实运行的发布 Loop。它从 MR 合并且人工验收通过开始，依次完成上线前检查、版本构建、升级预检与审批、目标版本确认、真实线上入口的冒烟测试，以及按改动范围选择的回归。所有证据成立后才标记发布完成。失败时要么取消升级，要么回滚到上一稳定版本并从同一线上入口复测。遇到权限、身份或生产风险，则交回人处理。**整个流程都通过我们的 LLM Wiki + Browser Automation skill 实现：**

1. 上线前先确定回滚和回归入口。记录目标 commit、本次行为变化、上一稳定版本，并确认线上使用哪个 Bot、哪个群、哪份群配置和哪组数据服务绑定。身份或群无法确认时暂停。
2. 创建版本并升级。先在 发布平台 核对发布权限、推荐版本、主线最新 commit 和检查结果，等待构建成功。部署平台 先做预检。纯版本发布只替换主仓版本，依赖仓和环境变量保持线上值，再执行真实升级。
3. 确认服务健康，再测真实入口。核对集群版本和健康状态，然后用线上 Bot、线上群和线上配置验证普通文本、卡片、数据服务 session、图片结果、服务绑定和降级路径。
4. 按改动范围回归并留证。除了新功能，还要回归已经证明过的关键路径。证据包括目标版本、集群状态、消息 ID、线上截图、logid、接口和数据库回读结果、未测项及原因。
5. 必要时回滚并复测。升级未生效时先判断能否取消。版本已经生效时，把主仓退回上一稳定版本，依赖仓和环境变量不动。回滚后仍从同一个线上入口重跑冒烟测试。
**3.10 收口：把交付事实留在 Repo**

一次交付完成后，最容易丢的往往不是代码，而是代码之外的因果关系：需求从哪里来，哪些决定被接受或推翻，原型为什么这样设计，怎样证明完成，线上到底验证过什么。收口时，我们会为这个 Issue 留下一份可以版本化、可以交接、也可以追溯的项目事实包。

我们的验收 README 已经证明了这种入口的价值。下一位 Agent 不必先读完几万字聊天，只要从 README 进入，就能找到实际分支、测试命令、消息 ID、Agent fileList、数据库和 Trace、失败复测以及未测项。现在我们把这个做法扩展到整个交付过程，而不只在验收前临时整理附件。

Coding 对话上传、自动设置 hook 和提交 checkpoint 都已有对应方案。这里同样暂不增加新的实体，先复用现有任务、Repo 和证据入口。

复杂 Issue 可以把交付材料放在 docs/issues/<issue-slug>/。这不是要求每个 Issue 都建齐所有目录，而是让同一种材料有稳定位置。下面是一份完整形态：

docs/

├── issues/<issue-slug>/

│   ├── README.md                 # 当前清单与稳定入口

│   ├── context/                  # 来源、对话摘要与脱敏原文

│   ├── decisions/                # 决定、理由与替代关系

│   ├── product/                  # PRD、原型、视觉合同与截图

│   ├── engineering/              # 最终 Spec、API 与数据约定

│   ├── verification/             # E2E 矩阵与测试拓扑

│   ├── execution/                # Plan 与当前进度

│   ├── acceptance/<run-id>/      # 每次验收的证据包

│   ├── release/                  # 上线、回滚与回归

│   └── operations/               # Runbook、观测与已知问题

├── E2E/                           # 项目的E2E测试全集

├── knowledge/                    # 项目专属知识

└── workflows/                    # 项目专属 SOP

**4. 交付之后：知识怎样进入下一次运行**

前三节先说明知识怎样被查询、在交付中验证，并回到项目事实源。仅仅写回材料仍不是知识改进 Loop。到了 4.4，运行样本开始反过来修改下一次 Loop，并由后续运行验证改动是否有效，反馈才真正闭合。

**4.1 开始前查询已有积累**

3.2 的上下文恢复，就是这条知识链的入口。比如后续需求再次涉及消息图片，Agent 应先从项目索引找到 P1b-7，再打开验收记录和相关 Spec，拿到已经被真实消息端、数据服务、数据库和 Trace 验证过的边界。只有这些材料仍解释不了某项取舍时，才回看原始会话。

**LLM-Wiki **在 Coding 中也承担这个作用。它不会把所有资料拼成一个超长 Prompt，而是用 Markdown、目录、索引和双向链接把信息分层。原始层保存讨论、Issue、MR、证据和外部文档。Wiki 页面压缩其中较稳定的事实与关系。治理规则说明先查什么、哪些内容属于哪个范围、证据有多可靠，以及何时可以提炼成共享经验。Agent 先找到相关实体，再按需打开来源。

**4.2 交付过程中验证并留下结构化痕迹**

知识只有回到真实交付里，才能知道是否成立。比如：P1b-7 中“续接 Task 可以补图”要同时经过真实图片、Agent fileList、Task、Trace 和消息回读才能确认。停机后的图片补录、多 Bot 共享缓存没有跑过，就只能留在未测项，不能升级成经验。

同样，旧 Workflow 可能漏了多 Bot，旧 Spec 可能没有覆盖无来源群，某条调试经验换了版本以后也可能失效。后续交付中的代码、测试、真实消息端、数据库和线上回归，会继续为这些判断增加证据，或者直接推翻它们。

执行过程中只整理会影响后续工作的痕迹：哪些决定被接受、拒绝或替代，原因是什么。实现与 Spec 有何偏差。失败时留下了哪些原始证据。复核发现了什么。真实 E2E、上线和回滚结果如何。还有哪些边界没有覆盖。完整聊天保留原始语境，当前有效的约定则由决定记录、Spec 和验收材料负责。

测试 case 也沿着这条链持续积累和修改。线上失败、人工纠正或新的产品边界出现后，要把对应 case 补进验证矩阵和回归集。旧 case 与新 Spec 冲突时，要修改或废弃，并保留原因。下一次 Loop 先运行与改动最相关的最小集合，进入 MR 和发布前再跑完整集合。这样，case 不只是一次性的验收清单，也是不断被真实交付校准的项目资产。

**4.3 项目事实回到 Repo**

项目事实分散在 个人Wiki 和仓库里，不适合多人共同维护，所以我们以类似 adr 的方式，将原始来源与对话摘要、关键决定、PRD、原型、Spec、验证矩阵、Plan、验收、发布记录、项目知识和项目 Workflow 都跟着代码放进 docs/ 并版本化（多步骤截图、录屏、Trace 包和原始日志等大文件上传到对象存储（对象存储），Repo 只保留稳定链接、run ID、生成时间、校验值和必要摘要。）。

中心 Wiki 保存全局索引、跨项目工程经验、共享流程、共享 Workflow 和提炼规则。项目事实只在 Repo 更新，Wiki 用链接和短摘要引用，避免同一内容维护两份。

每次上线完成后，提炼知识进入 Repo 的 docs/knowledge/ 、docs/workflows/（这里不会因为一次成功就直接写成通用规则）与docs/E2E/。

**4.4 知识改进 Loop：用运行样本改进下一次执行**

前三节解决的是知识从哪里来、在哪里保存，以及怎样被下一次真实交付验证。从这里开始，知识改进 Loop 才真正运行：定期读取 Coding Loop 的运行轨迹，找出总要纠正的步骤、没有带来状态变化的轮询、过大的回归集，以及高耗时、高 Token 却没有产生更强证据的执行，再定位 Loop 本身哪里不符合预期。每次运行继续保留目标、边界、实际步骤、人工介入、状态变化、日志和证据，作为下一次修改的依据。

E2E Loop 的运行复盘，这次复盘后，我们将流程中的全量回归改成了最小回归集

复盘只提出能够被轨迹支持的最小改动，例如删掉无效轮询、缩小回归集、补充停止条件、改进证据收集，或者调整某一步使用的模型。下一次运行时，在任务难度和验证方式大致可比的前提下检查结果质量是否保持，人工纠正、耗时和 Token 是否减少。成立才修改 Loop，否则撤回。运行次数不是积累，下一次更顺、更准、更省才是。

**5. 跑起来以后：注意点与尚未解决的问题**

这套流程不是从设计图里一次长出来的。很多规则都来自任务真正跑起来以后：一次回归耗掉几个小时，一次外部工具掉线让 Agent 原地重试，一次长程任务把电脑的内存和磁盘跑满，甚至导致机器关机。Loop 降低了重复执行的摩擦，也会把一次错误重复很多轮。

诚实地说，文章中有些部分其实不是一气呵成的，而是在实践中反复打磨的，所以这里必须说明一下，实践中的注意事项以及尚未解决的问题。

**5.1 每一轮先足够便宜**

Token 不是唯一成本，却最容易被 Loop 一轮轮放大。现在每次开跑前，Workflow 都会多问一句：这一步真的需要最强模型吗？图片和文本解析、格式转换、结果能够直接校验的小批处理，可以优先使用更便宜的模型或其他可用的推理资源。架构取舍、复杂编码和最终验收，再交给能力更强的模型。这不是一张固定的模型分工表。具体选择仍要看失败代价、任务判断难度，以及结果是否容易验证。

回归范围的分层也已经写进 Workflow。每次小改都跑全量测试，Loop 会很难收敛。运行中先选择能够推翻当前改动的最小安全回归集，改动碰到公共边界后再扩大范围，但进入 MR 和发布前仍跑完整回归。最小回归集不是少测，而是先用最小成本获得对当前假设最有区分度的反馈。

**5.2 长程任务先保证能活着跑完**

我们遇到过 Codex 长时间运行后把本机内存和磁盘打满，最后导致机器关机。此后，长任务起的heartbeat不只监控 Agent 有没有继续工作，还要监控目标进程树的内存、目标磁盘的剩余空间和产物增长。资源接近阈值时，先请求 checkpoint。线程已经卡死时，再按人预先授权的条件停止。当然，有条件的话换台内存和存储大一点的电脑吧.jpg

浏览器、MCP、认证、开发机、数据库和网络等外部工具如果不稳定，也会消耗大量时间和 Token。开跑前先做最短真实链路的预检，记录版本、身份和依赖状态，并在监控线程中设置重试上限。同一个错误连续出现且未解决时，应保存现场并交回人，而不是让 Agent 无限重试。

**5.3 拆分的是状态和验收边界**

任务拆分不只是把清单切成更多份。共享上下文很强、风险很低的小动作，直接在当前执行中完成。边界独立、可以并行、结果能由主线程复核的工作，交给 subagent（子 Agent）。需要长时间运行、独立权限、自己的停止条件和恢复入口时，再启用新 thread（claude -p 或 codex exec）。

另，人力有穷，但Loop可以无穷，以有涯随无涯，殆矣。所以刚开始自动化一个领域时，最好先做最小 Loop。先让一个 case 在一条短链路里闭合，积累真实的失败方式、证据和人工分叉，再逐步扩大并发、时长和覆盖范围。过早把所有步骤塞进一个大 Loop，只会让问题更难定位。

我们一开始的节奏非常好，一天解决两个issue，写两个spec，跑两趟loop。结果渐渐地，loop越来越大，写spec、跑loop、验收loop的时间都变得越来越长，最后再p1b-8这个issue里，达到了自己的上限。所以，也许Loop拆的稍小一点，跑的会更顺。

**5.4 朴素底座：最重要的是落盘**

长任务会经历上下文压缩、线程切换、工具故障和机器重启。没有落盘的状态，恢复时就只能重新猜。开跑前留下目标、边界、Spec、验证矩阵和 Plan。运行中持续写回进度、测试命令、失败现场、checkpoint 和 thread ID。结束时保存证据包、临时配置的恢复结果、未完成项和下一次入口。具体位置服从各仓库的 SOP，不要求所有项目使用同一个目录，但 Repo 中必须有一个稳定入口。

落盘也不等于把一切提交进 Git。PRD、Spec、索引、清单、可复跑脚本和少量代表性截图留在 Repo。多步骤截图、录屏、Trace 包和原始日志等大文件上传到对象存储（对象存储），Repo 只保留稳定链接、run ID、生成时间、校验值和必要摘要。上传后先回读确认可访问，再按 SOP 清理本地临时副本。否则一轮轮 E2E 不只会让 Git 仓库膨胀，也会把开发机磁盘拖垮。

E2E case 设计确实费劲。它需要同时写清用户能看到什么，API、数据库和运行状态中应该出现什么，以及失败后怎样复测。但这些 case 一旦落盘，就会变成可复用资产。后续的最小回归集、固定数据、截图基线、Trace 和发布回归都可以从中继续生长。每次线上失败如果只修代码、不补 case，Loop 就不会因为运行次数增加而变好。

这也是我们在 Coding 实践里越来越相信的朴素之道。最火的几套 Agent 工具的底座都比想象中简单：

- OpenClaw 先把普通 Markdown 文件作为跨会话记忆的事实层，再按需增加搜索和索引。
- Claude Code 用项目文件和 CLAUDE.md 保存长期约束，并直接借助 shell 与文件系统工作。
- LLM-Wiki 使用 Markdown、目录和双向链接保存知识，先加载索引，遇到具体问题再下钻。
- Hermes 把经验写成可以读取、修改和回滚的 SKILL.md，需要时再交给人审核。
《Are We Ready For An Agent-Native Memory System?》给这条经验补了一组更系统的证据。论文把 memory 拆成表示与存储、抽取、检索与路由、维护四个模块，对 12 套代表性系统和两条基线进行了实验，覆盖 5 类 workload 和 11 个数据集。**结果没有出现一种通吃所有任务的memory架构。**效果取决于 memory 结构是否对准当前 workload 的瓶颈。对有状态执行，保留操作过程和原始证据尤其重要。更复杂的结构还可能带来高出多个数量级的索引构建和查询延迟，却不一定得到相称的准确率提升。局部更新通常也比全局重组更划算。

这篇论文并不能证明 Markdown 永远优于知识图谱或复合 memory。它支持的是一个更窄的判断：在真实瓶颈出现以前，先保住可恢复的原始证据和局部可维护性，不要预先建设一套试图通吃所有场景的复杂系统。对这条 Coding Workflow 来说，朴素底座就是 Repo 里的 Markdown、Git、代码、测试、截图和运行记录。

**5.5 还没有解决的问题**

- 它仍要求人站在开发流程的前后。其实这也是合理的，毕竟你想要什么以及架构应该怎么定，Agent目前还没法直接解决，尤其是在没有积累足够的上下文之前。而我们设计spec和E2E测试时，也不一定能面面俱到，按照要求实现了spec之后，可能仍然需要介入E2E-Spec Loop的收尾。比如，我们验收的时候，就发现我们设计的时候，没有关注日期组件在中英文下的表现，最终的结果里，英文界面下，组件里出现了中文。
- 对于过大的loop，基本告别传统代码review。我们本次提交了几万行代码，很难真的和之前一样，认真地review。代码抽象的好不好，几乎全看plan review的好不好.jpg。虽然我们用了完整E2E验收报告来做review，但是我们也只能review的是关键决策、与原设计不同的意图、最终E2E的结果等聚焦的内容，至于代码是不是容易维护，是不是有什么边角case，这只能交给人的前置设计和模型来review了。也许这并不是不合理的方式，毕竟Agent在进步、上下文在累计，review也许只是人类失去掌控感时的挣扎罢了。
- 它不会自动解决并行开发中的代码冲突。 多个 Agent 或开发者同时改代码之前，仍要先划分模块、目录、接口和改动边界，明确哪些工作可以并行，哪些必须串行，以及交叉改动由谁合并。Workflow 可以记录并检查这些约定，但边界没有提前划清时，它无法阻止不同执行者改到同一处。另外，这套模式里，最好不区分前后端角色，否则流程上繁琐的对齐工作可能会摧毁这套工作流。
- 流程里的状态流转还没做，角色的划分也没做。我们期望是，这个issue上的人的个人Agent，共享上下文、issue状态流转，下游作为上游天然的检查者，不合格就打回，小的沟通也可以直接通过bot来投递。但是目前还在上下文的累计阶段，所有的角色都是我开多个thread里模拟的，所谓沟通也是我直接用codex的thread投递来模拟实现的。
- 从 0 到 1 的跨职能架构仍难把控。Loop 能把一个已知目标推向实现，却不会自动补上发起者在陌生技术领域里的判断。以我为例，做前端时除了几个基本限制，架构选择大部分只能选择看着靠谱的方式。Agent 最终可能交付一个能跑、能过测试的方案，但这不能证明架构本身适合长期演进。
- E2E case 的首次设计成本仍然很高。它会形成复利资产，但怎样更快地产出可靠的 case、事实判据和测试数据，还在持续完善。
- E2E 测试经过优化后仍然很吃 Token。跨端路径需要同时运行浏览器、Bot、API、数据库和运行时取证，单个 case 的成本仍然很高。最小回归集能减少无关执行，却不会消除真实链路本身的成本。
这些问题不会阻止我们使用 Loop，但会决定它适合跑到哪里。目标和验收明确、证据可以落盘的任务，可以继续扩大自动化。遇到陌生领域的架构判断、跨团队责任或成本过高的真实 E2E 时，Loop 应该把问题交回人，而不是用更多轮执行掩盖缺口。

**6. 团队化**

**6.1 Team Wiki Skill：把个人积累变成团队共同上下文**

目前我们的入口主要依赖个人 Wiki。它能让 Agent 跨会话恢复背景，但不适合团队共同维护。下一步先把边界划清：与代码强绑定的 PRD、原型、Spec、Plan、验收、发布记录、项目知识和项目 Workflow 进入仓库 docs/。Wiki 项目页只保留仓库地址、稳定入口和简短索引，继续负责跨项目知识和经验提炼。

在这个基础上，个人 Wiki 才能变成 Team Wiki Skill。它除了共享文档，还要统一团队的目录结构、查询顺序、写回方式和经验提炼流程。每个人的 Agent 接入后，都知道从哪里找到项目，怎样进入 Repo，哪些内容应写回 docs/，以及什么经验值得提交到团队知识库。

它可以有两种落地方式。一种是MonoRepo，把团队 Wiki 直接放进每个 Agent 的工作目录。打开项目时，Repo docs、团队知识和共享 Workflow 就在同一套文件系统里。另一种是维护一个独立的 team-wiki-skill Git 仓库，把 Wiki Schema、索引、共享知识、Workflow 和 Skill 一起版本化，由所有项目共同依赖。

无论它以挂载目录还是独立 Git 仓库存在，对 Agent 暴露的逻辑结构都可以保持一致（按需）：

team-wiki-skill/

├── SKILL.md                       # 触发、查询、写回与验收入口

├── AGENTS.md                      # 团队使用约束

├── index.md                       # 全局实体与导航

├── projects/

│   └── <project>.md              # Repo 地址、状态摘要、稳定入口

├── craft/                         # 跨公司可复用工程经验

├── internal/                      # 共享平台与流程

├── workflows/                     # 跨项目共享 Workflow

├── skills/                        # 已稳定的团队 Skills

├── schemas/                       # 页面与 frontmatter 契约

├── governance/

│   ├── query-order.md

│   ├── capture.md

│   ├── promotion.md

│   └── weekly-alignment.md

└── evals/

├── retrieval-cases/

└── skill-cases/

projects/ 不复制项目文档，只保存 Repo 地址、状态摘要和进入 docs/ 的稳定入口。craft/、internal/、workflows/ 与 skills/ 只接收经过真实交付验证、带来源和适用边界的提炼。这样两种部署方式共享同一套查询和写回协议。

无论采用挂载目录还是独立仓库，积累都从真实交付开始。每个 Issue 完成后，项目事实先随代码进入 Repo。只有经过验证、确实能在其他项目复用的经验，才带着来源、证据和适用边界进入团队库。这样，Team Wiki 会逐步成为所有 Agent 都能调用的团队知识入口，而不会复制第二份项目文档。

每个人的开发习惯都不同，团队成员甚至可以不用规约开发，但最终一定要把相关上下文按照规约schema保存。

**6.2 让团队的 Agent 在同一份上下文里协作**

一些团队化 Agent 平台已经在尝试提供统一的人机协作工作面和工作流程。完整 SDLC 的状态机、阶段产物、Gate、Worker Agent 与评论回流也都有对应方案。但我认为真正能提供给真实场景使用的agent，需要的不是多么fancy的平台、也不是所谓的Agent team与人机协作，而是团队真正积累、验证、迭代的开发上下文。古法 Coding 时代没有真正积累下来的项目上下文，到了 AI Coding 时代不会因为多了一个 Agent Team 自动出现。

所以第一步仍然是上一节的 Repo docs 和 Team Wiki Skill。前者保存与代码一起演进的 PRD、Spec、Plan、测试、证据和发布记录，后者保存跨项目 Workflow、Skill 和经过验证的经验。当 Repo docs、Team Wiki Skill、Workflow 和验收材料积累了足够多的上下文，下一步就不只是“每个人用自己的 Agent 写代码”，而是让这些 Agent 在同一套任务和知识入口上协作。每位成员可以开放已经配置好的 Agent，也可以使用一台长期在线的执行节点。**这些Agent本身其实并不需要区分角色，他们的上下文是一样的，只是我们仍需要按照人本身的责任来给Agent进行一些个责任划分并且对应上对应责任人的权限。**当然，人还是需要站在你的agent之后的。

团队以守护线程的形式，开放每位成员已经配置好的本地 Agent。这些 Agent 以issue为单位形式串起，围绕同一组带版本的事实源协作：

- Team Wiki 提供项目入口
- Repo docs 保存需求与接口
- Issue 记录任务认领和依赖
- Git 远端保存代码（包括Repo docs）状态。
这些 Agent 围绕同一个 Issue 队列工作，Agent 领取任务后，先从 Issue 确认仓库、基线提交和改动边界，再创建自己的分支与 worktree。形成检查点时，将代码推到远端，并把 head SHA、MR、测试结果和阻塞写回 Issue。下一位 Agent 据此恢复，而不是重新猜测前一个 Agent 做到了哪里。所以我们只需要设计一个守护队列服务(支持直接启动本机harness thread，除了轮询issue以外，需要以issue为支持基本的agent通信，类似codex的thread)、一套Agent能操作的状态流转CLI+自己本地最顺手的Agent Harness，不重新建设统一的操作面，这也是Agent时代我们一直坚持的“朴素”。

这些已有方案都值得直接评估复用。这里不展开具体平台，只保留一个判断：平台必须接得上同一份项目上下文和真实验收证据。

这条演进路径是连续的：先把一次 Issue 从需求走到上线，再把项目事实放回 Repo，把可复用经验提炼进 Team Wiki Skill，接着让团队内的个人 Agent共享同一个 Issue 队列和状态流转。Zara 在《别只给自己做 skill，请给你的上下游做 skill！》里说，个人用了 Agent，并不等于组织效率会同比提升，真正拖慢工作的往往是协同依赖。共享同一份上下文的价值，是让上下游少等待、少做重复转述。
